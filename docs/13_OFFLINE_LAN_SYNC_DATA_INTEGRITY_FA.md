# معماری آفلاین، شبکه محلی، چنددستگاهی و حل تعارض

## دو پروفایل اجرا، نه یک فرض مبهم
**Standalone Offline:** یک دستگاه با دیتابیس محلی؛ عملیات مجاز به‌صورت محلی ذخیره می‌شوند. ارقام در همان دستگاه معتبرند؛ گزارش مجموعه‌ای تا زمان انتقال/همگام‌سازی معتبر نمایش داده نمی‌شود.

**LAN Shared:** سرویس برنامه و پایگاه داده مرجع در رایانه/سرویس مرکزی داخل شبکه محلی. ایستگاه‌ها از API به آن متصل می‌شوند؛ قطع اینترنت نباید عملیات LAN را متوقف کند. این معماری با قرار دادن فایل دیتابیس SQLite روی پوشه share تفاوت دارد؛ فایل writable مشترک روی network filesystem ممنوع است.

**Sync/Transfer:** انتقال کنترل‌شده بین یک دستگاه مستقل و مرجع، شامل preview، UUIDهای رویداد، idempotency، mapping ارجاعات، duplicate detection، conflict queue و گزارش نتیجه. Sync موفق باید بر اساس receipt قابل اثبات باشد، نه فقط «upload started».

## مدل رویداد همگام‌شونده
هر رویداد قابل انتقال شامل entity UUID، event UUID، device ID، local sequence، entity version/revision، زمان دستگاه و زمان دریافت مرکزی (اگر موجود)، actor، نوع عملیات، payload version، references، idempotency key، origin/source، checksum و وضعیت sync است. timestamp واقعی فقط وقتی منبع معتبر دارد؛ clock drift شناسایی و برچسب‌گذاری شود.

## Outbox و inbox
تغییر محلی و outbox event در یک تراکنش ذخیره می‌شوند. ارسال می‌تواند دوباره retry شود؛ سرور inbox/processed-event به کمک event UUID و idempotency از اجرای تکراری جلوگیری می‌کند. پاسخ سرور شامل شناسه رسید، وضعیت پذیرفته/تکراری/رد/تعارض و خطای اعتبارسنجی است. رویداد ردشده از صف خاموش پاک نمی‌شود.

## Conflict policy
last-write-wins برای اسناد مالی/حسابداری ممنوع است. تعارض‌ها دسته‌بندی شوند: تغییر دوطرفه یک فیلد؛ ویرایش بعد از Post؛ شماره/کد یکتای تکراری؛ تخصیص هم‌زمان یک پرداخت؛ دو دستگاه با موجودی/مانده ناسازگار؛ مرجع حذف/غیرفعال‌شده؛ نرخ/الگوی متفاوت؛ ترتیب رخداد نامعلوم. هر مورد راه‌حل اختصاصی دارد: انتخاب مالک تغییر، merge فیلدی برای فیلدهای بی‌اثر، رد با علت، ایجاد اصلاحیه، یا بررسی دستی. اطلاعات مرجع/تعارض و مقدار قبل/بعد حفظ شود.

## شماره‌گذاری و شناسه
شناسه داخلی UUID پایدار است؛ شماره خوانای فاکتور می‌تواند در profile محلی prefix/sequence داشته باشد تا collision رخ ندهد یا هنگام sync شماره مرکزی تخصیص و شماره محلی به‌عنوان alias حفظ شود. پرامپت عامل باید این مسئله را قبل از پیاده‌سازی تصمیم‌گیری و مستند کند؛ تولید دو شماره ظاهراً یکسان ممنوع است. شماره سند قطعی نباید صرف retry عوض شود.

## انتقال Excel یا انتقال backup
انتقال batch با manifest شامل نسخه schema، منبع، تعداد رویدادها، checksum، وابستگی‌ها و زمان export. دریافت ابتدا validate-only و preview انجام می‌دهد؛ سپس transactionها commit می‌شوند. داده‌ای که به مرجع ناشناخته ارجاع دارد در quarantine می‌ماند. نتیجه باید تعداد accepted, duplicate, conflict, rejected, deferred و شناسه گزارش را ارائه کند. Backup image برای disaster recovery است، نه راهکار merge دو دیتابیس.

## سازگاری و محدودیت‌های امنیتی
- پایگاه مرجع و نسخه‌های local باید migration نسخه‌دار داشته باشند؛ client جدید با server قدیمی ناسازگار در سطح قابل تشخیص پیغام بدهد.
- Windows 7 در صورت باقی‌ماندن به‌عنوان نیاز legacy فقط با تست واقعی local/LAN؛ remote exposure از آن فرض نمی‌شود. دسترسی بیرونی از VPN/gateway امن و محیط پشتیبانی‌شده.
- هیچ‌وقت credential یا database file از طریق sync log/Excel ساده صادر نشود.
- sync باید در صفحه سلامت با شمار آخرین ارسال موفق، صف مانده، conflict، خطای آخر، نسخه schema و شناسه دستگاه نمایش داده شود.

## معیار پذیرش
قطع اینترنت در حالت LAN؛ قطع LAN در وسط ثبت محلی؛ restart قبل از ارسال outbox؛ retry بعد از پاسخ گم‌شده؛ duplicate event؛ دو دستگاه با یک پرداخت؛ تغییر حساب/Party آفلاین و غیرفعال شدن مرکزی؛ migration کلاینت؛ ساعت دستگاه اشتباه؛ export/import batch ناقص؛ بررسی مانده مرکزی تا قبل/بعد sync. در هر مورد، عدم فقدان/تکرار و گزارش صحیح نتیجه اثبات شود.
