# PROJECT_SPEC — Mazand FOS (خط مبنای محصول و اجرای سیستم)

**نسخه سند:** 4.0-Documentation Baseline · **زبان محصول:** فارسی RTL · **نوع محصول هدف:** ERP تخصصی عملیات مرکبات با حسابداری دوبل، خزانه، موجودی، گزارش و تبادل داده.

> این سند تعریف نیازمندی است و بیان نمی‌کند همه قابلیت‌ها در مخزن نرم‌افزار فعلی پیاده شده‌اند. وضعیت واقعی باید در audit ثبت شود. قبل از هر تغییر، `prompts/01_READ_ONLY_AUDIT_FA.md` اجرا و نتیجه تایید شود.

## 1. هدف و مرز محصول
Mazand FOS برای عملیات واقعی مازندشت طراحی می‌شود: برداشت باغ، ورود و باسکول، خرید، فروش، انبار، سورتینگ، بسته‌بندی، گردش سبد، ارسال امانی، گزارش فروش بارفروش، صافی، دریافت و پرداخت، بانک و چک، حسابداری دوبل و صورت‌های مالی؛ همچنین داده پایه، Excel/INFO، import/export، پشتیبان، sync چنددستگاهی، نصب و گزارش‌گیری.

این سامانه فقط دفتر ثبت نیست؛ هر رویداد باید ارتباط روشن بین سند تجاری، وزن/موجودی، طرف‌حساب، خزانه، تخصیص، سند حسابداری، گزارش و audit داشته باشد. ثبت در یک ماژول نباید با واردکردن دوباره همان داده در ماژول دیگر باعث اثر دوبرابر شود.

## 2. اصول غیرقابل‌نقض
1. ممیزی بدون تغییر قبل از پیاده‌سازی؛ حفظ تاریخچه Git و داده؛ branch جدا؛ هیچ تغییر مستقیم main.
2. حسابداری واقعی دوبل؛ Post قطعی فقط با توازن debit/credit. Draft نامتوازن به‌روشنی Draft می‌ماند.
3. سند قطعی از مسیر عادی edit/delete نمی‌شود؛ اصلاحیه/reversal با علت، کاربر، زمان و لینک به اصل.
4. شرط پرداخت، ابزار پرداخت، رویداد خزانه، تخصیص و JournalPosting مدل‌های جدا هستند.
5. حساب‌ها درختی و قابل‌تعریف با طبقه‌بندی، ماهیت مانده، ابعاد، نگاشت گزارش و تاریخ اعتبار صریح هستند؛ نام حساب کافی نیست.
6. مدل تسویه باید پشتیبانی کند: نقدی، نسیه، پیش‌پرداخت/علی‌الحساب، اقساط، چندمرحله‌ای، ترکیبی/چندابزاری، جزئی، تجمیعی، تخصیص‌نیافته/اضافه‌پرداخت، تهاتر، برگشت وجه، انتقال داخلی، چک و ارز.
7. بارفروش: ارسال، گزارش فروش طرف، وزن مبدأ/اعلامی، کمیسیون، هزینه‌های مستند، کسری/اعتراض، صافی جزئی و تجمیعی و پرداخت به‌هم مرتبط باشند؛ نرخ/قرارداد نسخه‌دار.
8. ریال واحد ذخیره پایه؛ تومان تبدیل نمایشی ثابت 10:1. ارز خارجی مبلغ اصل، نرخ تاریخ‌دار/منبع و مبلغ پایه جدا دارد.
9. وزن/افت/سبد فرمول مرجع دارد؛ gross vs net basis explicit است؛ آخرین تغییر بین loss-percent و loss-kg تعیین می‌کند کدام ورودی منبع محاسبه باشد.
10. موجودی حرکت‌محور؛ فاکتور خرید دستی در صورت نبود receipt باید فقط یک حرکت ورودی ایجاد کند؛ فروش خروجی است، نه ضایعات منفی. منفی بودن موجودی هشدار/استثناست و قفل عمومی نیست.
11. import بانک یا Match پیشنهادی اثر قطعی مالی نیست. بدون تایید، classification/post خودکار انجام نشود؛ تطبیق با پرداخت موجود اثر دوباره ایجاد نکند.
12. Excel قالب نسخه‌دار، mapping، preview، validation، duplicate/conflict handling و receipt import دارد؛ Office 2013 تنها پس از آزمون واقعی verified می‌شود.
13. Standalone Offline و LAN Shared دو پروفایل تعریف‌شده‌اند؛ انتقال/Sync UUID, idempotency, revision, conflict review و receipt دارد. last-write-wins برای اسناد مالی ممنوع؛ SQLite writable روی network share ممنوع.
14. UI باید premium, modern, graphical, RTL، full-height/workspace-based، سریع، با fixed action bar، جدول اسکرول داخلی، help/tooltip فارسی و quick-create drawer حفظ‌کننده Draft باشد.
15. Backup زمان‌بندی‌شده + هنگام خروج + پیش از عملیات پرخطر، checksum و restore drill واقعی دارد.
16. انتشار نیازمند migration rehearsal، tests, restore, installer, hashes, known limits و تایید انسانی است. عامل کدنویسی مجاز به push/publish بدون دستور صریح مالک نیست.

## 4. قراردادهای حیاتی کسب‌وکار
### 4.1 وزن و افت
For gross weight including baskets:
`basket_tare_total = basket_count * tare_snapshot`
`fruit_net = gross_scale_weight - basket_tare_total`
`loss_weight = fruit_net * loss_percent / 100` unless loss weight was last manually edited, in which case percent is derived.
`billable_weight = fruit_net - contractual_loss_weight - other_approved_weight_deductions`
`line_amount = billable_weight * unit_price` unless the approved document type explicitly selects a different price basis, which must be visible.

Reference example: 1500kg gross, 50 baskets × 10kg = 500kg tare, 1000kg net, loss 1%=10kg, 990kg billable. With 5kg tare, net=1250kg and loss=12.5kg, billable=1237.5kg. If scale input already represents net fruit, tare is not deducted again. Missing/negative/over-limit data must be validated and traceable.

### 4.2 Party dossier and quick create
One Party can have multiple roles. Selecting a party shows current/open balance, overdue, unallocated amounts, open invoices/safi, bank/cheque activity and full chronological history. Quick-create opens a side panel, stores parent draft, creates the master record, returns to the exact invoice/payment/safi context and selects the new record without losing table rows/focus/scroll.

### 4.3 Payment/settlement
Five separate concepts: PaymentTerms, PaymentInstrument, TreasuryTransaction, SettlementAllocation and JournalPosting. Support N:M allocations; partial payment; multiple payments per invoice; one payment allocated to multiple documents; advance before invoice; unallocated credits; mixed cash/bank/cheque/credit; installments; offsets/contra; refunds; own-account transfers; currency; cheque lifecycle. Allocation cannot exceed unallocated source/target without an explicitly modeled approved credit/adjustment.

### 4.4 Barforoosh safi
Safi is a versioned, auditable settlement result, not a single freeform amount. Components: confirmed sales, commission formula/version, freight, approved expenses and receipts, contractual shortage/returns/claims, previous advances/payment allocations and documented adjustments. Keep outbound and reported sales weights distinct. Multi-load safi and partial safi per load. Any final change after posting is an amendment/reversal, never silent edit.

### 4.5 Accounts and reports
Account class/type, normal balance, posting eligibility, required dimensions, control/subledger type, financial statement mapping, current/noncurrent rule, closing rule and currency policy are explicit. Four-column trial balance = debit/credit movements and debit/credit balances. Six-column trial balance = opening debit/credit, period movements debit/credit, closing debit/credit. Balance sheet is not trial balance. Missing data is not zero; unverified cost policy means profit estimated/unfinalized.

## 5. UX baseline
Dashboard with clickable real KPIs and drilldowns; stable RTL shell; role-based workspaces; large well-labeled controls; fixed header and action bar; internal table scrolling; contextual Persian help; clear Draft/Approved/Posted/Reversed/Sync Pending/Conflict/Bank Unmatched/Estimate states. Critical actions not icon-only. All screens require loading, empty, error, permission-denied, offline, unsynced and conflict states. Mock values only in explicitly marked demo environment.

## 6. Platform/offline/data integrity
Standalone mode owns local state; LAN mode uses central API and database with no dependency on public internet; controlled sync joins them through event UUID/idempotency and conflict resolution. Reports label whether local or central/fresh. Do not claim shared instant totals across isolated devices. Windows 7 is legacy compatibility only where actual tests pass; no secure remote access promise. Remote access from supported hosts via VPN/secure gateway.

Every Critical requirement needs code path, data persistence, permission/audit, tests, actual artifacts and migration/rollback where relevant. Not-run or blocked is never pass.

## تعارض‌های شناخته‌شده که باید بی‌سروصدا حل نشوند
1. پشتیبانی Windows 7 در برابر امنیت مدرن remote: Local/LAN تا حد تست؛ اتصال بیرونی امن فقط روی محیط پشتیبانی‌شده و از راه VPN/gateway.
2. استقلال آفلاین در برابر داده مشترک چنددستگاهی: دفتر محلی مستقل است؛ تا sync تاییدشده عدد مشترک/مانده همگانی نیست.
3. «یک‌باره کامل» در برابر اجرای ایمن: هدف دامنه کامل است اما پیاده‌سازی در برش‌های عمودی قابل اجرا/بازگشت انجام می‌شود.
4. تمایل به فرم منعطف در برابر حفاظت حسابداری: انعطاف UI مجاز است؛ قواعد double-entry، مجوز، ردپای حسابرسی و یکپارچگی قابل خاموش‌شدن نیستند.
5. وزن بارفروش/مبدأ: هر دو مقدار و منبعشان حفظ شود؛ یکی بی‌صدا جایگزین دیگری نشود.
6. نرخ کمیسیون/هزینه: نسخه قرارداد و تاریخ اعتبار ذخیره شود تا با تغییر نرخ جاری، تسویه قبلی بازنویسی نشود.

## تصمیم‌های مالی نیازمند تایید تخصصی قبل از Go-Live
اینها نباید جلوی ساخت شالوده نرم‌افزار را بگیرند، ولی قبل از انتشار واقعی صورت‌های مالی/سود قطعی باید تایید شوند: کدینگ آغازین واقعی؛ مانده افتتاحیه؛ قواعد طبقه‌بندی صورت وضعیت مالی؛ روش قیمت تمام‌شده (پیشنهاد فعلی میانگین موزون متحرک محصول/درجه × انبار)؛ طبقه‌بندی جریان وجوه نقد؛ نحوه ثبت ضایعات و هزینه سورتینگ/نگهداری؛ مالیات/عوارض و فرمت قانونی فاکتور؛ نرخ‌ها/رویه چک‌های برگشتی؛ سیاست بستن سال و انتقال سود؛ شیوه ثبت سهم مالک/برداشت شخصی. تا تایید، گزارش مرتبط باید «غیرنهایی/برآوردی» علامت بخورد.

## مرجع مثال وزن
- مثال مبنای تصمیم: وزن ناخالص شامل سبد `1500 kg`، تعداد سبد `50`، وزن خالی هر سبد `10 kg`: وزن سبد `500 kg`؛ وزن خالص میوه `1000 kg`; افت 1% = `10 kg`; وزن قابل‌حساب `990 kg`.
- اگر وزن سبد به‌ازای هر سبد 5kg باشد، با همان 50 سبد، کسر سبد `250 kg` و وزن خالص `1250 kg` است؛ با افت 1%، وزن افت 12.5kg و قابل‌حساب 1237.5kg خواهد بود. مثال دوم جایگزین اول نیست؛ نشان می‌دهد وزن سبد باید صریح/نسخه‌دار باشد.

# مشخصات عملیات واقعی مازندشت و گردش‌کارهای متصل

## دامنه و اصطلاحات کارگاهی
محصول برای مجموعه مازندشت و گردش مرکبات طراحی می‌شود: برداشت باغ، خرید از باغدار/تأمین‌کننده، قبض باسکول، ورود به انبار (از جمله انبارهای وابسته به مسئول/محل)، شست‌وشو و ضدعفونی، گرمادرمانی/انبارداری، سورت، تفکیک درجه، بسته‌بندی/سبد، فروش عمده، ارسال به مشتری یا بارفروش، اعلام فروش و دریافت صافی، دریافت/پرداخت و گزارش مالی. انواع پرتکرار کالا شامل تامسون، نارنگی، والنسیا، پرتقال خونی، لیمو و سایر انواع مرکبات است؛ فهرست باید داده پایه قابل‌ویرایش باشد، نه enum ثابت.

## اشخاص و نقش‌های تجاری
یک Party برای هر شخص/شرکت/بازار با چند نقش هم‌زمان نگهداری شود: مشتری، تأمین‌کننده/باغدار، بارفروش، حمل‌کننده، کارمند، مالک/شریک، طرف قرارداد، بانک/مرجع. پروندۀ شخص شامل نام و نام مستعار، شناسه یکتا، تلفن/آدرس، نقش‌ها، وضعیت فعال، شروط پرداخت، سقف اعتبار، اسناد و فایل‌های پیوست، مانده دفترکل/معین، گردش عملیاتی، ریز بانک و رویدادهای مهم است. نقش جدید نباید نیاز به ایجاد پرونده تکراری داشته باشد.

## گردش‌های انتها به انتها
### برداشت باغ خودی
1. ایجاد حواله برداشت با باغ/قطعه/تاریخ/نوع مرکبات/کیفیت/وزن/مسئول و در صورت وجود هزینه برداشت.
2. ثبت باسکول یا وزن دستی دارای منبع و کاربر.
3. رسید به انبار و ایجاد گردش ورود.
4. ثبت هزینه‌های مستقیم (چیدن، سبد، حمل و کارمزد) به مرکز هزینه/محصول طبق سیاست مصوب؛ AP خارجی به‌طور پیش‌فرض ساخته نشود.
5. مقایسه وزن ورودی و وزن پذیرفته‌شده؛ اختلاف به صف بررسی برود.

### خرید از تأمین‌کننده
1. انتخاب طرف حساب از lookup مشترک با چند نقش و نمایش مانده/فاکتورهای باز.
2. قبض باسکول، وزن سبد و فرمول خالص/افت؛ یک ردیف برای هر نوع محصول.
3. وضعیت Draft → کنترل وزن/کیفیت → بررسی قیمت/شرایط → تأیید/ثبت قطعی.
4. فاکتور خرید و گردش موجودی به هم پیوند می‌خورند؛ اگر کاربر فاکتور را دستی بدون قبض قبلی بسازد، ثبت قطعی طبق مجوز باید گردش ورود را از همان ردیف‌ها بسازد، با یک شناسه واحد و بدون ثبت دوباره.
5. بدهی تأمین‌کننده ایجاد می‌شود؛ پرداخت نقدی، حواله بانکی، چک، پیش‌پرداخت و تخصیص بعدی مجزاست.

### فروش مستقیم
1. انتخاب مشتری و مشاهده مانده، فاکتورهای باز و اعتبار.
2. انتخاب نوع فروش: نقدی، نسیه، قراردادی، پیش‌فروش/علی‌الحساب یا قالب سفارشی.
3. ردیف کالا و سبد، وزن و افت قراردادی، قیمت، تخفیف/هزینه و مبنای قابل‌حساب.
4. کنترل‌های هشدار موجودی منفی و قیمت/تخفیف غیرعادی بدون قفل عمومی؛ کنترل‌های ویژه بر اساس سیاست/مجوز.
5. سند فروش/حواله خروج/ثبت دریافت از هم متمایز می‌مانند و به هم لینک می‌شوند.

### ارسال امانی به بارفروش و صافی
1. بارفروش و قرارداد/نسخه نرخ کمیسیون انتخاب می‌شود.
2. هر بار دارای شماره یکتا، بارنامه/قبض خروج، وزن مبدأ، نوع سبد، محصول و محل مقصد است.
3. گزارش فروش بارفروش (یک یا چند بار) وارد و با ارسال مقایسه می‌شود؛ وزن ارسالی و وزن اعلام‌شده هرگز یکی فرض نمی‌شوند.
4. صافی شامل مبلغ فروش تأییدشده، کمیسیون، کرایه، افت/کسری، هزینه‌های مستند، علی‌الحساب‌ها و مبلغ خالص قابل پرداخت/دریافت است.
5. هزینه‌های اعلامی با تاریخ، مدرک و تایید؛ سقف قرارداد قابل تعریف و هزینه خارج سقف به صف هشدار می‌رود.
6. صافی می‌تواند جزئی باشد و چند بار را تجمیع کند؛ مانده هر بار/قرارداد و وضعیت اختلاف حفظ می‌شود.
7. پس از تأیید صافی، سند حسابداری مرتبط ساخته/پیشنهاد می‌شود؛ تا Post مجاز، در دفترکل اثر قطعی ندارد.
8. پرداخت بعدی، تخصیص به صافی/فاکتور/علی‌الحساب رویداد مجزا دارد.

## صفحه طرف‌حساب: رفتار پایه
به‌محض انتخاب شخص در فاکتور/پرداخت، پنل جزئیات شامل مانده جاری، مبلغ سررسید گذشته، اسناد باز، پرداخت تخصیص‌نیافته، چک‌های مرتبط و آخرین رویدادها باز شود. مرتب‌سازی پیش‌فرض جدیدترین به قدیمی‌ترین است؛ فیلتر بازه/نوع/وضعیت دارد. سطرها قابل انتخاب‌اند تا پرداخت به یک یا چند بدهی تخصیص یابد. مانده منفی با متن واضح و راهنمای معنی نمایش داده شود، اما به‌طور عمومی ثبت را مسدود نکند.

## الگوهای ثبت اطلاعات
- برگه عملیاتی باید «حداقل فیلدهای لازم برای انجام کار» را در حالت ساده و جزئیات را در پنل بازشونده نشان دهد.
- داده پایه در لحظه ایجاد سند قابل تعریف سریع است؛ پس از ذخیره، کاربر به فرم اصلی بازمی‌گردد و پیش‌نویس، ردیف‌های جدول، اسکرول و مقادیر قبلی حفظ می‌شود.
- هر ذخیره/قطعی‌سازی idempotent است: دوبار کلیک یا retry اتصال نباید سند/اثر موجودی/سند حسابداری تکراری بسازد.
- هر سند یک `DocumentNumber` خوانا و یک `DocumentUUID` پایدار دارد؛ شناسه‌های مبدأ/مقصد (قبض، فاکتور، حواله، صافی، پرداخت، سند GL) در پانل «ارتباطات» قابل دنبال‌کردن‌اند.

# قرارداد تخصصی تعریف حساب‌ها، کدینگ و داده پایه مالی

## اصل طراحی
کدینگ حساب یک درخت داده‌ای مستقل از ظاهر فرم و مستقل از نام فارسی حساب است. هیچ طبقه‌بندی مالی نباید از متن عنوان مثل «بانک»، «هزینه» یا «جاری» حدس زده شود. هر حساب باید ویژگی‌های صریح داشته باشد و تغییر ویژگی‌های مالی حساس سابقه و اثر بازنگری را نگه دارد.

## فیلدهای لازم هر حساب
- `account_id` UUID ثابت؛ `account_code` یکتا و قابل جست‌وجو؛ `account_name_fa` اجباری؛ عنوان انگلیسی/نام مستعار اختیاری.
- `parent_account_id`؛ سطح یا نوع گره (گروه/کل/معین/تفصیلی یا درخت انعطاف‌پذیر با سطوح مجاز تنظیم‌شده)؛ `account_type` صریح مانند Asset, Liability, Equity, Revenue, ContraRevenue, Expense, ContraExpense, Clearing.
- `normal_balance` بدهکار/بستانکار؛ `posting_allowed`؛ `active_from/to`؛ `status` فعال/غیرفعال/آرشیو؛ توضیح و مالک تصمیم.
- `statement_mapping`: طبقه صورت وضعیت مالی/سودوزیان/حقوق مالکانه/جریان وجوه نقد؛ `current_noncurrent_policy` با منبع تعیین (ویژگی حساب یا قاعده سررسید)؛ قواعد بستن و انتقال مانده.
- `required_dimensions`: Party، BankAccount، CostCenter، Warehouse، Product/Grade، Contract، Load/Consignment یا هیچ‌کدام؛ اعتبارسنجی قبل از Post.
- `subsidiary_control_type`: کنترل دریافتنی، پرداختنی، بانک، صندوق، چک، موجودی، دارایی ثابت، حساب واسط یا none؛ کنترل جمع دفتر معین با GL.
- `currency_policy`: ارز پایه تنها یا ارزهای مجاز؛ `allow_manual_journal`; `requires_approval`; `tax/reporting flags` در صورت نیاز و پس از تعیین سیاست.
- audit fields: ایجادکننده/زمان، آخرین تغییر، دلیل تغییر، نسخه، تغییرات قبلی، approver برای حساب‌های حساس.

## قواعد ساخت درخت
1. کد حساب در کل دفتر/شرکت یکتا است. تغییر کد نباید شناسه داخلی را عوض کند؛ اسناد سابق با شناسه پایدار و کد تاریخی قابل بازبینی می‌مانند.
2. حساب دارای فرزند معمولاً برای ثبت مستقیم مجاز نیست؛ فقط اگر سیاست کدینگ صریحاً اجازه دهد.
3. حساب سیستمی/کنترلی قابل حذف فیزیکی نیست؛ غیرفعال‌سازی برای ثبت جدید مجاز، نمایش سابقه و گزارش باز مجاز می‌ماند.
4. تغییر از «ثبت مجاز» به «غیرقابل ثبت» باید قبل از قطعی‌سازی، وجود Draftهای وابسته، templateهای ثبت و import mapping را بررسی کند.
5. حساب‌های Control برای اشخاص/بانک/چک/موجودی نباید با ثبت دستی نامرتبط قابل ایجادِ مغایرت شوند؛ manual journal روی حساب کنترل به دسترسی بالاتر و توضیح نیاز دارد.
6. در تعریف تفصیلی شناور، پرونده Party/Bank/Contract منبع واحد است؛ ایجاد حساب تفصیلی تکراری برای یک شناسه مجاز نیست مگر تصمیم حسابدار صریحاً مدل متفاوتی بخواهد.

## موتور نگاشت حساب خودکار
هر رویداد تجاری باید به یک `PostingTemplate` نسخه‌دار اشاره کند. فیلدهای الگو: نوع رویداد، شرط فعال‌سازی، حساب بدهکار/بستانکار یا resolver، ابعاد الزامی، وضعیت Draft/Post، روش محاسبه مبلغ پایه، قواعد گردکردن، سازگاری با ارز، reverse mapping، گزارش هدف، مالک و تاریخ اعتبار. قالب می‌تواند برای «فاکتور خرید»، «فروش مستقیم»، «پرداخت به تأمین‌کننده»، «پیش‌پرداخت»، «دریافت تخصیص‌نیافته»، «صافی بارفروش»، «کارمزد بانک»، «برگشت»، «تعدیل موجودی» متفاوت باشد.

### مثال‌های حسابداری برای آزمون (مشروط به سیاست کدینگ)
- خرید نسیه: بدهکار موجودی/خرید طبق سیاست ارزش‌گذاری، بستانکار حساب پرداختنی طرف؛ اثر موجودی و AP هر کدام فقط یک بار.
- پرداخت بدهی: بدهکار AP همان طرف و بستانکار بانک/صندوق/حساب واسط پرداخت؛ اگر چک صادر شده هنوز وصول/تحقق نشده، lifecycle چک و حساب کنترلی مصوب مبنا قرار گیرد.
- فروش نسیه: بدهکار دریافتنی مشتری، بستانکار درآمد/مالیات و کسورات مطابق فاکتور مصوب؛ اثر خروج موجودی/COGS جداگانه از سند درآمدی، طبق سیاست حسابداری.
- دریافت از مشتری قبل از فاکتور: بدهکار بانک/صندوق، بستانکار پیش‌دریافت یا دریافت تخصیص‌نیافته؛ با تخصیص بعدی، فقط جابه‌جایی درست بین حساب‌ها انجام شود، نه دریافت دوباره.
- تراکنش بانک واردشده: تا شناسایی و تایید، در صف تطبیق است؛ import statement به‌تنهایی نه درآمد است و نه پرداخت قطعی.

## کنترل‌های گزارش و دوره
صورت وضعیت مالی از نگاشت explicit و قواعد جاری/غیرجاری استفاده می‌کند. تراز آزمایشی چهارستونی: گردش بدهکار، گردش بستانکار، مانده بدهکار، مانده بستانکار. شش‌ستونی: مانده بدهکار/بستانکار اول دوره، گردش بدهکار/بستانکار، مانده بدهکار/بستانکار پایان دوره. هر دو باید جمع‌های کنترلی و فیلتر تاریخ/دفتر/وضعیت را نشان دهند. ناهماهنگی معین با حساب کنترلی GL باید در گزارش «مغایرت دفتر معین و کل» بیاید.

# قرارداد مالی: مدل پرداخت، دریافت، شرایط پرداخت و تخصیص

## یک تفکیک بنیادی: پنج شیء متفاوت
سیستم باید این پنج مفهوم را به‌صورت داده و صفحه جدا اما مرتبط پیاده کند:
1. **شرایط پرداخت (`PaymentTerms`)**: توافق تجاری با طرف؛ نقدی، نسیه با سررسید، اقساط، پیش‌پرداخت درصدی/مبلغی، چندمرحله‌ای، اعتباری/قراردادی، تسویه از طریق بارفروش، یا ترکیبی. شرایط، تعهد مورد انتظار است؛ خودش انتقال پول نیست.
2. **ابزار پرداخت (`PaymentInstrument`)**: روش اجرا: نقد صندوق، کارت‌خوان/POS، حواله/انتقال بانکی، چک دریافتی/صادره، تهاتر، برگشت وجه، پرداخت ارزی، ابزار سفارشی که مدیر تعریف می‌کند. «ابزار» به معنی ثبت وقوع یا تخصیص نیست.
3. **رویداد خزانه (`TreasuryTransaction`)**: دریافت، پرداخت یا انتقال واقعی/درحال‌انتظار با حساب مبدأ/مقصد، زمان واقعی، شماره مرجع، مبلغ، ارز، کارمزد، طرف حساب، وضعیت و مدرک. انتقال بین دو حساب خود سازمان درآمد/هزینه نیست.
4. **تخصیص (`SettlementAllocation`)**: پیوند یک رویداد دریافت/پرداخت/اعتبار به یک یا چند فاکتور، صافی، پیش‌پرداخت، بدهی یا سند. این پیوند مستقل است و به‌صورت N:M یا جدول واسط با مبالغ تقسیم‌شده اجرا می‌شود.
5. **اثر دفترکل (`JournalPosting`)**: ثبت مالی پیشنهادشده، پیش‌نویس یا قطعی. ثبت خزانه یا تخصیص نباید اثر دوباره ایجاد کند. وضعیت منبع و وضعیت GL جداست و در UI هم جدا نشان داده می‌شود.

## مدل‌های قابل تعریف
- **نقدی کامل:** رویداد فروش و دریافت می‌توانند در یک گردش کار ایجاد شوند، ولی دو رکورد و دو اثر حسابداری شفاف دارند؛ ذخیره دوباره یا retry نباید receipt دوباره بسازد.
- **نسیه با سررسید:** فاکتور تعهد ایجاد می‌کند؛ دریافت آینده جداست؛ سنی مطالبات/بدهی و تاریخ سررسید قابل گزارش است.
- **پیش‌پرداخت/علی‌الحساب:** قبل از فاکتور ممکن است؛ به حساب پیش‌پرداخت/پیش‌دریافت و طرف مربوط متصل می‌شود؛ تا تخصیص، آزاد/تخصیص‌نیافته می‌ماند.
- **اقساط/چندمرحله‌ای:** زمان‌بندی دارای مبلغ، تاریخ، درصد/مبلغ، وضعیت، جریمه/هزینه فقط در صورت وجود سیاست مصوب، و شناسه تعهد است. مجموع اقساط باید با مبلغ پایه/شرط قرارداد اعتبارسنجی شود؛ تغییر مبلغ فاکتور به محاسبه مجدد با نشان‌دادن اختلاف نیاز دارد.
- **ترکیبی/چندابزاری:** یک تسویه می‌تواند چند tender داشته باشد؛ نمونه: قسمتی نقد، قسمتی کارت‌خوان، قسمتی چک و باقی نسیه. مجموع اجزا در لحظه ثبت باید با مبلغ اعمال‌شده و مانده قرارداد همخوان یا با «مبلغ تخصیص‌نیافته/اضافه‌دریافت» صریح باشد.
- **پرداخت جزئی و پرداخت تجمیعی:** یک پرداخت می‌تواند به چند فاکتور تخصیص یابد و یک فاکتور با چند پرداخت پوشش داده شود. باقی‌مانده هر دو طرف حفظ می‌شود.
- **اضافه‌پرداخت/اعتبار آزاد:** مبلغ مازاد را بی‌اجازه به فاکتور تصادفی نچسبانید؛ در وضعیت Unallocated Credit با انتخاب بعدی، تاریخچه و مانده واقعی نشان داده شود.
- **تهاتر/offset:** دو تعهد را بر مبنای سند تهاتر و اجازه کاربر مجاز کاهش می‌دهد؛ آن را به‌عنوان دریافت بانکی جعلی ثبت نکنید.
- **استرداد/برگشت وجه:** مرجع پرداخت اولیه و علت الزامی؛ رویداد خزانه معکوس و سند برگشت قابل ردیابی. پاک‌کردن پرداخت اولیه ممنوع.
- **انتقال داخلی:** حساب مبدأ/مقصد خود سازمان، شماره انتقال یکتا، هزینه بانک جدا. انتقال باید به شکل جفت debit/credit یا انتقال treasury واحد با دو اثر متوازن اجرا شود، نه پرداخت به تأمین‌کننده.
- **پرداخت ارزی:** مبلغ ارز اصلی، نرخ معتبر تاریخ‌دار و منبع نرخ، مبلغ پایه ریالی و تفاوت تسعیر جدا. ریال/تومان در این مدل، FX محسوب نمی‌شود.
- **پرداخت چکی:** ثبت دریافت چک به‌تنهایی مساوی وجه نقد وصول‌شده نیست؛ وضعیت‌های lifecycle و حساب کنترل چک بر اساس تایید سیاست حسابداری اعمال می‌شود.

## وضعیت و انتقال حالت
برای TreasuryTransaction حداقل وضعیت‌ها: `Draft → Validated → Confirmed/Posted`؛ برای چک وضعیت تخصصی جداست. رد/ابطال باید دلیل داشته باشد و اگر Post شده reversal ساخته شود. تخصیص‌ها حالت Draft/Confirmed/Reversed دارند. باید invariantها تعریف شوند: مجموع تخصیص‌های تاییدشده از مانده رویداد تجاوز نکند، مجموع تخصیص به سند از مانده قابل تخصیص بیشتر نشود مگر سیاست اضافه‌تخصیص صریحاً داشته باشد، و reversal شناسه تخصیص اولیه را نگه دارد.

## فرم دریافت و پرداخت (UX)
هدر: نوع عملیات دریافت/پرداخت/انتقال، طرف حساب (اختیاری برای انتقال داخلی)، تاریخ/ساعت واقعی، روش/ابزار، حساب صندوق/بانک، مبلغ و ارز، مرجع بانکی/چک، شماره رسید، کارمزد، شرح، پیوست، ایجادکننده و وضعیت. پنل «تخصیص» فهرست فاکتورها/صافی‌ها/پیش‌پرداخت‌های باز را جدیدترین‌به‌قدیمی‌ترین نشان می‌دهد؛ هر سطر مبلغ سند، پرداخت قبلی، مانده باز، مبلغ تخصیص فعلی، تاریخ سررسید و وضعیت را دارد. انتخاب چند ردیف و تخصیص جزئی پشتیبانی شود. خلاصه ثابت پایین: مبلغ رویداد، تخصیص‌شده، آزاد/اضافه‌پرداخت و باقی‌مانده. کلیک روی طرف، پنل پرونده را در همان فضای کار باز می‌کند و بعد از ثبت به فرم پرداخت بازمی‌گردد.

## قواعد کنترل مالی
- تاریخ رویداد خزانه، تاریخ سند تجاری، تاریخ ثبت و زمان ورود فایل صورت‌حساب از هم تفکیک شوند.
- واردات صورت‌حساب بانک رویداد خام می‌سازد، نه حسابداری قطعی؛ match پیشنهادی باید با درصد/دلایل مطابقت، وضعیت رد/پذیرش و duplicate detection همراه باشد.
- مبلغ/تاریخ/شماره مرجع مشابه duplicate candidate ایجاد می‌کند؛ هشدار به معنی حذف خودکار نیست.
- تغییر حساب بانکی یا روش پرداخت بعد از Post با اصلاحیه/برگشت انجام شود.
- هیچ نرم‌افزاری به‌خاطر صرفا صفر شدن مانده یک طرف‌حساب نباید سند مستقل دیگری بسازد.
- باید آزمون invariant شامل «دو کلیک»، retry شبکه، واردات مجدد فایل، چند تخصیص هم‌زمان و reversal وجود داشته باشد.

## سناریوی مرجع
خرید 100 میلیون ریال نسیه است. خریدار/پرداخت‌کننده 30 میلیون را به بانک حواله می‌کند، 20 میلیون چک می‌دهد و 10 میلیون اضافه به‌عنوان علی‌الحساب می‌فرستد. سیستم باید 30 میلیون رویداد بانک + تخصیص به فاکتور؛ 20 میلیون چک با lifecycle؛ و 10 میلیون اعتبار آزاد جدا داشته باشد. جمع پرداخت‌های نقدشده/غیرنقدشده، مبلغ تخصیص‌شده، مبلغ تعهد باقی و مبلغ اعتبار آزاد یکسان تلقی نشوند. این سناریو نمونه آزمون مدل است، نه ثبت واقعی شرکت.

# قرارداد صافی بارفروش/فروش امانی، کمیسیون، کسورات و اختلاف

## مدل تجاری
ماژول بارفروش باید هم قرارداد فروش قطعی به بارفروش و هم ارسال امانی برای فروش نهایی را پشتیبانی کند. هر محموله دارای نوع رابطه و نسخه قرارداد است. در حالت امانی، انتقال محصول به بارفروش خودبه‌خود به معنی درآمد قطعی/فروش نهایی نیست مگر سیاست حسابداری مصوب آن را تعیین کند. فروش گزارش‌شده، برگشتی، مانده نزد بارفروش و صافی‌های ناقص باید مجزا باشند.

## شناسه‌ها و ارتباطات
`ConsignmentContract` (طرف، شرایط، نرخ کمیسیون، سقف هزینه، مبنای وزن، تاریخ اعتبار) ← `Load/Dispatch` (UUID، شماره قابل چاپ، تاریخ، قبض باسکول، انبار مبدأ، محصول/درجه، تعداد و نوع سبد، وزن‌ها، راننده/خودرو/رسید) ← `BarforooshSalesReport` (یک/چند بار، ریز محصول، وزن/تعداد فروخته‌شده، قیمت، برگشت، مدرک) ← `SafiSettlement` (فروش مبنا، کسورات خط‌به‌خط، پرداخت/علی‌الحساب قبلی، مبلغ خالص، مانده باز، تایید) ← `TreasuryTransaction` و `JournalPosting`. هر صفحه باید نوار ارتباطات زنجیره‌ای با یک کلیک داشته باشد.

## نسخه‌بندی شرایط
نرخ کمیسیون می‌تواند درصد مبلغ فروش، نرخ ثابت بر کیلو، سبد، بار یا روش قراردادی باشد؛ روش پلکانی در صورت نیاز نیز مدل‌پذیر است. هر نرخ شامل تاریخ شروع/پایان، شرط دامنه، مبنای محاسبه و نسخه قرارداد است. تغییر نرخ جدید نباید صافی قبلی یا ارسال‌های قبل از تاریخ اثر را تغییر دهد. اگر نرخ برای محموله override شود، دلیل و مجوز ثبت شود.

## اجزای محاسبه صافی
برای هر محموله/گزارش فروش، اجزا به سطرهای مجزا نگهداری شوند:
- `gross_sales_amount`: فروش تأییدشده بر مبنای گزارش.
- `commission`: مبلغ/نرخ/مبنای محاسبه و نسخه قرارداد؛ نمایش فرمول و رُندکردن.
- `freight_and_transport`: کرایه مستند با مرجع/طرف پرداخت‌کننده.
- `approved_weight_shortage_or_loss`: کسری/افت مورد پذیرش طبق نوع و مبنای قراردادی؛ با افت فاکتور خرید یا ضایعات فیزیکی مخلوط نشود.
- `documented_expenses`: ریز هزینه، تاریخ، مبلغ، شرح، مدرک، ثبت‌کننده و تاییدکننده؛ سقف/هزینه غیرمجاز flag شود.
- `previous_advance_or_payment`: پرداخت‌ها/علی‌الحساب‌هایی که واقعاً به همین رابطه تخصیص داده شده‌اند؛ هر پرداخت فقط یک بار.
- `returns_or_claims`: برگشت/اعتراض و وضعیت حل‌شده/باز.
- `net_settlement`: حاصل قاعده نسخه‌دار قرارداد، نه یک فیلد دستی بدون breakdown.

فرمول کلی قابل‌پیکربندی: `net payable = confirmed sales − commission − approved freight − approved expenses − contractually accepted shortage/returns − allocated advances/payments ± documented adjustments`. اگر نقش اقتصادی «مبلغ قابل دریافت از بارفروش» باشد جهت مانده برعکس نمایش داده می‌شود. رابط باید جهت طلب/بدهی را روشن کند و صرفا علامت منفی را بدون برچسب رها نکند.

## مبنای وزن و اختلاف
وزن خروجی مازندشت و وزن اعلامی بارفروش هر دو با تاریخ، منبع، واحد، توضیح و سند حفظ شوند. اختلاف کیلو و درصد اختلاف محاسبه شود؛ صفر یا نبود مقدار معادل هم نباشد. پرونده اختلاف شامل مقدار مورد اختلاف، علت انتخابی/آزاد، مدارک، مسئول پیگیری، تاریخ ایجاد/آخرین اقدام، اعتراض/پاسخ، تصمیم و تاییدکننده است. اصلاح داده قدیمی تنها برای اشتباه ثبت اولیه و با مجوز/نسخه مجاز است؛ در موارد تسویه نهایی از اصلاحیه یا صافی متمم استفاده شود.

## تسویه جزئی و تجمیعی
- یک صافی می‌تواند چند محموله را شامل شود؛ هر جزء به بار/فروش خاصی نسبت داده شود.
- یک محموله می‌تواند در چند مرحله تسویه شود؛ مبلغ انجام‌شده و مانده باز هر محموله باقی بماند.
- پرداخت می‌تواند به یک صافی، چند صافی یا اعتبار آزاد تخصیص یابد؛ مبلغ تخصیص از مبلغ خزانه بیشتر نشود.
- بستن صافی نیازمند تعیین تکلیف سطرهای هزینه، کسری، اعتراض و مانده است؛ «صفرشدن مانده» به‌تنهایی اثبات تسویه صحیح نیست.

## ثبت حسابداری
صافی Draft محاسبه و پیش‌نمایش دارد؛ Confirmed به معنی تایید تجاری است؛ Posted به معنی سند ثبت‌شده در دفترکل. هر مرحله واضح نمایش داده شود. پس از Confirm/Posted تغییر مستقیم ممنوع؛ اصلاحیه صافی و در صورت نیاز reversal/adjustment ایجاد شود. سند حسابداری باید به تمام اجزای محاسبه و منابع مرتبط drill-down داشته باشد. حساب‌های مورد استفاده از الگوی مصوب بارفروش و کدینگ واقعی انتخاب می‌شوند، نه hard-code عنوان حساب.

## گزارش‌های الزامی
- بارهای باز به تفکیک بارفروش، عمر مانده و وضعیت اختلاف.
- صافی به تفکیک هر محموله و صافی تجمیعی با مبلغ ناخالص، تک‌تک کسورات، پرداخت/علی‌الحساب و خالص.
- مغایرت وزن مبدأ در برابر گزارش فروش/صافی، درصد اختلاف و نتیجه بررسی.
- هزینه‌های غیرعادی یا خارج سقف؛ هزینه بدون مدرک؛ override نرخ کمیسیون.
- صافی تاییدشده بدون سند GL یا سند GL بدون صافی منبع؛ تخصیص پرداخت تکراری.

## معیار پذیرش
باید آزمون شود: 3 محموله در یک صافی، یک محموله در دو صافی جزئی، تغییر نرخ قرارداد پس از ماه گذشته، هزینه بدون رسید، هزینه بیش از سقف، اعتراض باز، پرداخت مشترک برای دو صافی، صافی تکراری از retry، اصلاح پس از Post و تطبیق مجموع اجزا با مبلغ خالص تا کوچک‌ترین واحد پولی مجاز.

# قرارداد فاکتور تخصصی مرکبات، باسکول، وزن، افت، قیمت و اثر موجودی

## قواعد داده هر ردیف فاکتور
هر سطر فقط یک نوع محصول/درجه دارد؛ ترکیب انواع مرکبات در یک سطر ممنوع است. ستون‌های استاندارد: محصول، درجه/کیفیت (در صورت استفاده)، تعداد سبد/ظرف، نوع سبد، وزن خالی هر سبد از نسخه داده پایه، وزن کل سبد محاسبه‌شده، نوع وزن ورودی، عدد باسکول/وزن ناخالص، وزن خالص میوه، درصد افت، وزن افت، سایر کسورات وزنی مصوب، وزن قابل‌حساب، واحد قیمت، نرخ، تخفیف/هزینه‌های سطر، مبلغ سطر و نشانگر هشدار/override. ستون‌های محاسباتی read-only عادی هستند اما اصلاح دستی کنترل‌شده ممکن است، با دلیل و audit.

## تعاریف وزن
- `gross_scale_weight`: عدد ثبت‌شده باسکول که نوع آن در سند مشخص است؛ همیشه فرض نشود ظرف در آن منظور شده.
- `basket_tare_total = basket_count × tare_per_basket` فقط وقتی ظرف/سبد داخل وزن ناخالص است و روش اندازه‌گیری این را تایید می‌کند.
- `fruit_net_weight = gross_scale_weight − basket_tare_total` برای وزن ناخالص شامل ظرف. اگر باسکول وزن خالص میوه می‌دهد، مدل `weight_basis` باید آن را روشن کند تا کسر دوباره سبد ممنوع شود.
- `loss_weight = fruit_net_weight × loss_percent / 100` وقتی درصد آخرین ویرایش است.
- `loss_percent = loss_weight / fruit_net_weight × 100` وقتی مقدار کیلو آخرین ویرایش است و خالص غیرصفر است.
- `billable_weight = fruit_net_weight − contractual_loss_weight − approved_other_weight_deductions`; هیچ رقم ناموجود را خودکار صفر معنایی ندهید، مگر صفر صریحا ثبت شده باشد.
- `line_amount = billable_weight × unit_price` سپس تخفیف/هزینه براساس الگوی نوع فاکتور اعمال شود. مقدار مبنای قیمت (ناخالص، خالص یا قابل‌حساب) برای هر نوع سند قابل پیکربندی، در UI قابل مشاهده و در Snapshot ذخیره شود.

## مثال‌های ثابت آزمون
**مثال 1، مبنای تصمیم:** gross=1500kg شامل سبد؛ 50 سبد × tare 10kg = 500kg؛ fruit net=1000kg؛ loss=1%=10kg؛ billable=990kg.

**مثال 2:** همان gross=1500kg و 50 سبد، اما tare=5kg: tare total=250kg؛ fruit net=1250kg؛ loss 1%=12.5kg؛ billable=1237.5kg. این تفاوت باید از داده پایه یا وزن واقعی نسخه‌دار ناشی شود، نه تغییر پنهان فرمول.

**مثال 3، وزن خالص از باسکول:** gross field عملا به معنی fruit net ثبت شود؛ `weight_basis=NET_FRUIT`; tare فقط برای کنترل تعداد/سبد گزارش می‌شود و دوباره از وزن کم نمی‌شود.

## رفتار هوشمند محاسبه
1. اگر درصد افت تغییر کند، وزن افت و وزن قابل‌حساب بلافاصله محاسبه شوند.
2. اگر وزن افت (kg) دستی تغییر کند، درصد افت مجدداً محاسبه شود. آخرین فیلد دست‌خورده تعیین می‌کند کدام داده منبع محاسبه است. این وضعیت در مدل با `loss_input_mode=PERCENT|WEIGHT` ثبت شود.
3. تغییر تعداد/نوع سبد، tare یا نوع وزن، وزن خالص و تمام خروجی‌های وابسته را مجدداً محاسبه کند؛ قبل از overwrite عدد دستی باید هشدار/بازبینی داده شود.
4. جدول کوچک «جزئیات فرمول» نشان بدهد: مبنای وزن، gross، tare، net، درصد/کیلو افت، سایر کسورات و billable. کاربر نباید صرفا نتیجه نهایی را ببیند.
5. اعداد با precision داخلی کافی ذخیره شوند؛ گردکردن فقط در مرزهای تعریف‌شده، با سیاست واحد/پول و آزمون مرزی انجام شود. برای وزن‌های اعشاری، نمایش و precision به تنظیمات قابل مدیریت وابسته است.
6. `tare_per_basket` و loss default از نسخه تاریخ‌دار داده پایه گرفته شوند؛ سند ذخیره‌شده Snapshot مقادیر واقعی مورد استفاده را حفظ کند تا تغییر بعدی در master data فاکتور قدیم را عوض نکند.
7. نبود tare: Draft ذخیره‌پذیر است، اما ثبت قطعی با هشدار/قفل تخصصی طبق تصمیم موجود باید کنترل شود؛ پرسش‌نامه بین اجازه پیش‌نویس و جلوگیری از نهایی‌سازی تمایز می‌گذارد. رفتار دقیق نهایی طبق Decision Register و نقش کاربر پیاده شود.

## گزینه «عدم کنترل افت بار»
این flag به معنی حذف وزن، حذف سابقه یا نادیده گرفتن فیزیک نیست. باید معنای تنظیمی شفاف و قابل گزارش داشته باشد: برای محصول/قرارداد، هشدار آستانه افت اعمال شود یا نشود؛ حتی اگر کنترل آستانه خاموش است، مقدار افت و منبع آن ثبت می‌ماند. هر مقدار خارج از حدود مرجع به‌صورت warning/exception با کاربر/مجوز/علت قابل بازبینی است. سیستم حق ندارد loss را بی‌صدا صفر کند یا از موازنه مقدار حذف کند.

## نوع سند و وضعیت
خرید، فروش مستقیم، برگشت خرید، برگشت فروش، قبض باسکول، حواله خروج، انتقال انبار، ثبت برداشت و صافی بارفروش نوع سندهای مشخص دارند. وضعیت نمونه: Draft → WeightChecked → CommerciallyApproved → Posted/Committed؛ گذار دقیق باید برای هر نوع سند تعریف شود. Draft اثر قطعی روی دفترکل یا موجودی ندارد، مگر reservation جداگانه و شفاف. Posted قابل ویرایش مخرب نیست.

## ایجاد گردش ورود هنگام فاکتور دستی
اگر خرید دستی از قبل قبض ورودی مرتبط نداشت، نهایی‌سازی فاکتور باید گردش ورود موجودی را از همان ردیف‌ها با idempotency key ایجاد کند. اگر قبض از قبل به فاکتور لینک شده، ورود دوم ایجاد نشود. UI ارتباط source-of-stock را نشان بدهد و گزارش exception هر purchase بدون حرکت یا هر حرکت بدون سند منبع ارائه شود.

## آزمون‌های وزنی اجباری
- تعداد سبد صفر و tare خالی؛ محصول بدون سبد؛ count منفی/کسری اعشاری نامعتبر.
- gross < tare؛ وزن خالص صفر/منفی؛ افت بزرگ‌تر از وزن خالص؛ percent بیش از محدوده configured.
- ورود وزن net و gross؛ تغییر نوع وزن پس از واردکردن اعداد؛ فاکتور با دو محصول و دو نوع سبد.
- درصد افت و سپس ویرایش kg افت و بالعکس؛ تغییر تعداد سبد پس از ویرایش دستی؛ save/reopen و حفظ دقیق ارقام.
- تکرار کلیک نهایی، خطای شبکه و retry؛ نباید ورود/فروش/GL دوباره ایجاد شود.
- تطبیق وزن billable با مبلغ سطر و گزارش چاپی؛ واحد وزن و واحد قیمت در خروجی و XLSX یکسان باشند.

# طرف‌حساب‌ها، داده پایه، الگوهای تعریف و ثبت سریع

## پرونده یکپارچه شخص/شرکت
از ساخت پرونده‌های جدا برای یک فرد به خاطر نقش متفاوت جلوگیری شود. Party یک هویت مرکزی با شناسه پایدار است؛ PartyRole رابطه او با کسب‌وکار را مشخص می‌کند. نقش‌ها می‌تواند مشتری، تأمین‌کننده/باغدار، بارفروش، متصدی حمل، فروشنده کالا/خدمت، کارمند، شریک/مالک یا نقش سفارشی باشد. تغییر نقش، اسناد گذشته را پاک یا با ماهیت جدید بازتفسیر نمی‌کند.

## فیلدهای Party
کد یکتا؛ نام رسمی/نام نمایشی؛ نام مستعار/بازاری؛ نوع شخص حقیقی/حقوقی؛ شناسه‌های قانونی فقط در صورت نیاز و امن؛ تلفن‌های متعدد با نوع؛ نشانی/شهر؛ روش ارتباط؛ نقش‌ها؛ گروه قیمت/قرارداد؛ شرایط پرداخت پیش‌فرض؛ سقف اعتبار؛ ارز پیش‌فرض؛ اطلاعات حمل/تحویل؛ وضعیت فعال؛ توضیح؛ فایل‌های قرارداد و اسناد؛ تگ‌های قابل تعریف؛ زمان و کاربر ایجاد/تغییر. فیلدهای حساس باید ماسک، مجوزدار و در audit ثبت شوند.

## تعریف Party وسط فرم بدون گم‌شدن Draft
- از lookup، کاربر «تعریف سریع» را باز می‌کند؛ پنل جانبی در همان workspace باز شود، نه صفحه‌ای که فاکتور را تخریب کند.
- پیش‌نویس والد در state/durable draft ذخیره موقت و به یک `return_context_id` پیوند داده شود.
- فرم سریع فقط فیلدهای ضروری را نشان بدهد و دکمه «تعریف کامل» جدا داشته باشد.
- پس از ذخیره، Party جدید به فرم والد برگردد و خودکار در فیلد مربوط انتخاب شود؛ سطرهای فاکتور، مقادیر قبلی، فوکوس، اسکرول و مرحله حفظ شود.
- اگر Party مشابه پیدا شد، سیستم گزینه‌های احتمالی و فیلدهای همخوان را نشان بدهد؛ ادغام خودکار ممنوع. کاربر می‌تواند پرونده قبلی را انتخاب کند یا ایجاد تازه را با دلیل مجاز انجام دهد.
- cancel، خطا یا بسته‌شدن پنل نباید رکورد ناقص اصلی بسازد؛ داده Draft موقت و هشدار خروج ذخیره شود.

## استاندارد داده پایه
کالا، درجه، واحد، سبد، بانک، حساب بانکی، صندوق، کدینگ حساب، مرکز هزینه، انبار، علت ضایعات، نوع قرارداد، شرط پرداخت، روش پرداخت، نوع سند، قالب چاپ، دسته گزارش، نوع طرف حساب و قالب Import همگی باید CRUD مدیریت‌شده داشته باشند. برای هر داده پایه: کلید پایدار؛ کد یکتا در scope؛ نام فارسی؛ عنوان انگلیسی اختیاری؛ وضعیت فعال؛ تاریخ اعتبار در موارد مالی؛ ترتیب نمایش؛ قوانین validation؛ پیوندهای وابسته؛ زمان/کاربر و نسخه. اگر داده در سند ثبت‌شده استفاده شده، حذف فیزیکی ممنوع و غیرفعال‌سازی به‌جای آن باشد.

## انتخاب‌گرهای هوشمند
Search باید بر اساس کد، نام رسمی، نام مستعار، تلفن مجاز، شناسه بار، شماره فاکتور و تگ کار کند؛ ورودی فارسی/انگلیسی، نیم‌فاصله، ارقام فارسی/لاتین و فاصله‌های رایج نرمال‌سازی شوند بدون اینکه مقدار اصلی از دست برود. جست‌وجو باید قابل استفاده با صفحه‌کلید و برای فهرست زیاد صفحه‌بندی/مجازی‌سازی‌شده باشد. هر نتیجه نقش، کد و نام را نشان دهد تا افراد همنام اشتباه انتخاب نشوند.

## نمای گردش طرف‌حساب
Timeline از جدیدترین رویداد به قدیمی: فاکتور خرید/فروش، قبض، دریافت/پرداخت، انتقال، چک، صافی، برگشت، سند دستی مرتبط، پیوست، اختلاف و یادداشت پیگیری. فیلتر زمان/نوع/وضعیت، خروجی مجاز و Drill-down وجود داشته باشد. مبلغ «تخصیص‌یافته»، «تخصیص‌نیافته»، «مانده باز»، «سررسید گذشته» و «مانده دفترکل» جداگانه تعریف شوند. اگر مانده طرف‌حساب منفی است، لحن هشدار باید توضیح دهد منظور بستانکاری/اضافه‌پرداخت است؛ صرف علامت منفی بدون متن کافی نیست.

## کنترل duplicate و ادغام
نام مشابه به‌تنهایی کلید یکتا نیست. برای کد، شناسه قانونی، شماره موبایل نرمال‌شده و شناسه واردشده، duplicate candidates نمایش داده شود. Merge فقط با مجوز بالاتر، dry-run که تعداد و انواع اسناد متاثر را نشان دهد، نقشه حفظ شناسه‌ها، سابقه تصمیم و rollback/جبران‌پذیری انجام شود. هیچ اسناد مالی قطعی صرفا با merge به شکل خام بازنویسی نشوند.

# موتور حسابداری دوبل، دفترکل، صورت‌های مالی و بستن دوره

## لایه‌های مالی
1. رویداد تجاری/عملیاتی منبع (فاکتور، صافی، دریافت/پرداخت، چک، تعدیل).
2. Posting proposal مبتنی بر الگوی ثبت نسخه‌دار.
3. سند حسابداری Draft قابل اعتبارسنجی.
4. Posted journal که فقط خطوط متوازن و مجاز را ثبت می‌کند.
5. دفترکل و دفترهای معین/تفصیلی از خطوط Posted تولید می‌شوند.
6. گزارش مالی از ledger و نگاشت حساب/دوره، همراه با مسیر بازگشت به سند منبع محاسبه می‌شود.

نباید برای گزارش، داده مالی جداگانه‌ای ایجاد شود که با دفترکل ناسازگار شود. اگر cache/materialized view استفاده شده، قابل بازسازی و قابل تطبیق باشد. Draft روی گزارش قطعی GL اثر ندارد؛ می‌تواند در گزارش «اسناد در انتظار ثبت» مجزا دیده شود.

## ساختار سند GL
شماره یکتا، UUID، تاریخ سند، دوره مالی، تاریخ/زمان ایجاد، سازنده، وضعیت، منبع و source UUID، نوع الگوی ثبت و نسخه، شرح، ارز/مبلغ پایه در صورت نیاز، lines شامل حساب، بدهکار، بستانکار، party/dimensions، شرح سطر، مرجع line، پیوست و lineage. قواعد: مبالغ غیرمنفی؛ یک طرف بدهکار یا بستانکار طبق مدل هر line؛ مجموع بدهکار برابر مجموع بستانکار در precision پایه؛ ارز خارجی با مبلغ اصل و مبلغ پایه/نرخ تاریخ‌دار؛ dimension اجباری برای حساب‌های کنترلی؛ تکرار source posting با idempotency key ممنوع.

## ثبت قطعی و اصلاح
- Draft را می‌توان اصلاح و حذف کرد، مگر policy نگهداری خاص.
- Post فقط پس از validation و permission و کنترل دوره مجاز است.
- Posted journal از مسیر عادی UPDATE/DELETE نمی‌شود. اصلاح از طریق reversal یا adjustment با لینک به اصل، دلیل، کاربر، زمان و مجوز است.
- reopen دوره فقط با مجوز ویژه و audit؛ گزارش تغییر دوره قبل/بعد و اثر روی خروجی‌ها لازم است.
- هر تغییر الگوی ثبت باید تاریخ اعتبار و نسخه داشته باشد؛ الگوی جدید سند قدیمی را دوباره تولید نمی‌کند.

## گزارش‌های پایه
- دفتر روزنامه و دفترکل با Drill-down از حساب → سطر → سند → منبع.
- کارت حساب و گردش طرف‌حساب/معین، مانده اول دوره، گردش دوره و مانده پایان.
- تراز آزمایشی 4 ستونی: گردش بدهکار، گردش بستانکار، مانده بدهکار، مانده بستانکار.
- تراز آزمایشی 6 ستونی: اول دوره بدهکار/بستانکار، گردش دوره بدهکار/بستانکار، پایان دوره بدهکار/بستانکار.
- صورت وضعیت مالی/ترازنامه: گروه‌بندی طبق mapping explicit؛ جاری/غیرجاری با قاعده تعریف‌شده و در موارد سررسیدمحور طبق سررسید/چرخه عملیات.
- سود و زیان: درآمد، کاهنده درآمد، بهای تمام‌شده و هزینه با تفکیک محصول/انبار/مشتری/بارفروش/مرکز هزینه هرجا ابعاد به‌درستی ثبت شده باشد.
- جریان وجوه نقد: از رویدادهای واقعی و mapping طبقه‌بندی؛ انتقال بین حساب‌های خود سازمان نباید به‌عنوان نقد عملیاتی ناخالص دوباره شمرده شود.
- تغییرات حقوق مالکانه؛ سنی‌سازی مطالبات و بدهی؛ گردش و مانده اسناد چک.
- تطبیق معین با حساب کنترلی GL؛ اسناد نامتوازن؛ سند قطعی بدون منبع یا منبع بدون GL؛ دوره بسته؛ ثبت تکراری؛ مانده واسط کهنه؛ سند با بعد الزامی خالی.

## نحوه نمایش نقص داده
صفر واقعی `0` است؛ مقدار نامعلوم/مفقود `null` یا `Unknown` است و نباید به صفر تبدیل شود. اگر سود به خاطر بهای تمام‌شده ناقص قابل محاسبه قطعی نیست، نشان «برآوردی/غیرنهایی» با علت و عوامل مفقود نمایش داده شود. خروجی باید فیلترهای applied، تاریخ مبنا، روش هزینه، وضعیت سند، ارز/واحد و زمان تولید را چاپ کند.

## بستن دوره
Checklist قبل از close: تمام عملیات Draft/ناموفق تعیین تکلیف؛ مانده صندوق/بانک و reconciliation؛ چک‌های باز؛ مانده طرف‌حساب/GL؛ موجودی و تعدیلات تاییدشده؛ واسط/تعلیقی و قدیمی‌ها؛ درآمد/هزینه انتقالی/پیش‌پرداخت؛ گزارش‌های کنترلی؛ بکاپ قبل از بستن. Close باید قفل ثبت در بازه/نوع را اعمال کند. Reopen به علت و مجوز نیاز دارد و audit را حفظ می‌کند.

## هزینه موجودی و سود
پیشنهاد فنی پیش‌فرض: میانگین موزون متحرک در سطح محصول/درجه × انبار، اما قبل از انتشار سود رسمی باید با حسابدار، موجودی افتتاحیه، هزینه حمل/سورت/بسته‌بندی/انبارداری و سیاست تخصیص تایید شود. هزینه تخصیص‌ناپذیر و هزینه دوره‌ای را قاطی نکنید. تا تایید سیاست، گزارش سود باید واضحاً «برآوردی» باشد.

# خزانه، بانک، چک و تطبیق صورت‌حساب

## داده پایه بانک و حساب بانکی
BankAccount دارای شناسه ثابت، عنوان، بانک/شعبه، شماره حساب/شبا به‌صورت محافظت‌شده و ماسک‌شده در UI، دارنده، ارز، حساب دفترکل مرتبط، تاریخ شروع/پایان و وضعیت فعال است. مانده دستی قابل ویرایش فقط به‌عنوان مانده افتتاحیه/اصلاحیه مستند ثبت شود؛ رقم مانده روزانه باید از گردش‌های تاییدشده و تطبیق صورت‌حساب قابل بازسازی باشد.

## تفکیک گردش بانک از سند حسابداری
یک ردیف فایل صورت‌حساب `BankStatementLine` ابتدا رویداد import است؛ شامل شناسه batch/import، منبع فایل، نام شیت/شماره ردیف، تاریخ بانکی، تاریخ ارزش اگر باشد، شرح خام، مبلغ ورودی/خروجی، ارز، مانده بانک (اگر فایل دارد)، شماره مرجع، checksum و hash هویت تکرار. این ردیف هنوز معلوم نمی‌کند عملیات خرید، فروش، انتقال، کارمزد یا پرداخت بوده است. عملیات «تطبیق» و «تولید/تایید سند GL» گام‌های جدا هستند.

## تطبیق نیمه‌خودکار
سیستم می‌تواند candidateهای مشابه را با مبلغ، تاریخ (بازه قابل تنظیم)، شناسه، بانک/طرف‌حساب و شرح پیشنهاد کند. هر پیشنهاد شامل امتیاز/دلایل match و لینک به سند محتمل است. اپراتور Confirm/Reject/Defer می‌کند؛ اگر نامعلوم است، ردیف در صف باقی می‌ماند. match چندبه‌یک یا یک‌به‌چند فقط وقتی مبلغ و قرارداد تطبیق را رعایت می‌کند مجاز است؛ اختلاف کارمزد، split payment یا ادغام bank settlement باید خط‌های جزئی و دلیل داشته باشد.

## جلوگیری از اثر دوباره
- صورت‌حساب بانکی که پرداختی را منعکس می‌کند ممکن است با رویداد پرداختی موجود match شود؛ در این حالت سند پرداختی جدید نسازید.
- اگر تراکنش هنوز در سیستم موجود نیست، پس از تایید کاربر رویداد خزانه یا سند مناسب ایجاد می‌شود و به line bank پیوند می‌خورد.
- کارمزد بانک یک جزء مجزا با سند/الگوی ثبت است؛ مبلغ اصلی بانکی را به‌تنهایی به کارمزد تبدیل نکنید.
- انتقال بین حساب‌های سازمان باید دو سمت را جفت کند و نباید به درآمد یا هزینه تلقی شود.
- واردکردن مجدد همان فایل/ردیف باید duplicate detection داشته باشد و بدون تایید مجدد اثر مالی نسازد.

## مرکز چک و چرخه عمر
چک ورودی/صادره دارای شماره/سریال، بانک، حساب/شعبه، مبلغ، ارز، تاریخ صدور، سررسید، طرف مرتبط، سند/رویداد مبدأ، متصدی، وضعیت و مدرک است. وضعیت‌های موردنیاز، متناسب با نوع، شامل ثبت اولیه، نزد صندوق، واگذاری به بانک، وصول، برگشت، واگذاری/خرج‌کرد، ابطال پیش از اثر نهایی، جایگزینی و پیگیری است. هر گذار زمان/کاربر/مرجع و اثر دفترکل کنترل‌شده دارد. تفسیر «چک صادر شد» با «وجه از حساب خارج شد» یکسان نیست؛ سیاست حسابداری آن باید صریح و نسخه‌دار باشد.

## سررسید و هشدارها
نمای روز/هفته/ماه برای چک‌های دریافتی و صادره؛ سررسید گذشته؛ وضعیت نامعلوم؛ چک برگشتی؛ چک واگذار شده ولی وصول تایید نشده؛ چک جایگزین و اصل؛ مبلغ در معرض ریسک. هشدار می‌تواند نقش‌محور باشد و در صورت تنظیم به داشبورد/اعلان درون برنامه بیاید؛ سیستم نباید اطلاعات چک/شماره کامل را برای نقش غیرمجاز افشا کند.

## تطبیق و بستن بانک
چک‌لیست دوره‌ای: مانده دفترکل اول دوره، مانده صورت‌حساب، تراکنش‌های matched، موارد بانک‌داری‌شده ولی هنوز در سیستم، پرداخت ثبت‌شده اما خارج از صورت‌حساب، کارمزد/بهره، تراکنش‌های باز و اختلاف نهایی. گزارش اختلاف باید هر خط را شامل تاریخ، شناسه، مبلغ، مرحله بررسی، مسئول و دلیل داشته باشد. بسته‌شدن تطبیق یک snapshot با کاربر/زمان دارد؛ ورود داده تازه بعد از close موجب بازبینی یا نسخه جدید می‌شود.

## فیلدهای صورت‌حساب/گردش
نام بانک و حساب ماسک‌شده، تاریخ واقعی بانک، تاریخ ثبت در سیستم، شرح خام و شرح اصلاح‌شده، مبلغ ورودی/خروجی جدا، ارز، مرجع، وضعیت match، لینک رویداد خزانه، لینک سند GL و فیلتر بازه. در نبود زمان دقیق منبع، زمان ساختگی تولید نکنید؛ تنها timestamp ثبت سیستم مجاز است.

# گردش موجودی، سورتینگ، ضایعات، بسته‌بندی و سبد

## Ledger گردش محصول
موجودی از جمع حرکت‌های معتبر محاسبه می‌شود؛ field عدد موجودی به‌صورت مرجع دستی قابل ویرایش نباشد. هر `InventoryMovement` شامل UUID، محصول/درجه، انبار، تاریخ عملیاتی، تاریخ ثبت، مقدار/واحد، جهت، نوع رویداد، سند منبع، از/به، وضعیت، batch/idempotency، سازنده، علت و در صورت نیاز مقدار/هزینه پایه است. اگر ردیابی محموله واقعی ثبت نشده، ارتباط دقیق یک فروش با یک باغ/بار ادعا نشود.

## انواع رویداد موجودی
ورود خرید، برداشت باغ خودی، برگشت فروش، پذیرش اصلاحی؛ خروج فروش، ارسال امانی، مواد مصرفی؛ انتقال بین انبارها با دو طرف linked؛ سورتینگ با ورودی و خروجی‌های چنددرجه‌ای؛ بسته‌بندی/مصرف ظرف؛ ضایعات واقعی؛ رزرو (وضعیت جدا از موجودی فیزیکی)؛ موجودی در راه؛ تعدیل شمارش مصوب؛ برگشت به تأمین‌کننده. هر نوع رویداد وزن‌ها/حساب‌های لازم را مشخص کند.

## موازنه وزن و محصول
باید بتوان گزارش تجمعی تهیه کرد: مجموع وزن‌های ورودی به تفکیک محصول/انبار/بازه، مجموع خروجی فروش/ارسال، ضایعات واقعی، برگشتی‌ها، انتقال خالص و تعدیلات؛ اختلاف و علت/شرح. خروجی فروش را به‌عنوان «ضایعات منفی» یا کسری مصنوعی ثبت نکنید. وزن ورودی و خروجی باید بر اساس همان واحد و مبنای مشخص مقایسه شود. نوع محاسبه موازنه هنگام تبدیل محصول خام به درجه‌های مختلف باید rule مشخص داشته باشد و به‌صورت تبدیل واحد/گرید مستقل ثبت شود.

## موجودی منفی و کسری
مطابق تصمیم موجود، موجودی منفی به‌صورت هشدار و صف استثنا نمایش داده می‌شود و فروش را به‌طور عمومی قفل نمی‌کند. این مجوز، مجوز پاک‌کردن کسری یا ثبت بی‌سند نیست. exception شامل کالا، انبار، مقدار منفی، اولین تاریخ وقوع، اسناد عامل، مسئول و نتیجه است. تعدیل فقط با شمارش فیزیکی/علت/تاییدکننده ایجاد شود. گزارش اختلاف نباید به‌تنهایی سند حسابداری ایجاد کند.

## سورت و تبدیل درجه
برای عملیات سورتینگ یک سند کار با ورودی‌های محصول/وزن، خروجی‌های هر درجه، پرت/ضایعات فیزیکی، وضعیت کیفیت، کاربر/خط، زمان شروع و پایان و در صورت ثبت، مواد/هزینه مصرف‌شده ثبت شود. مجموع ورودی باید با خروجی‌ها+ضایعات+باقیمانده کار در حد تلورانس تعریف‌شده موازنه شود. تلورانس بر حسب نوع کار و اندازه‌گیری تنظیم‌پذیر است؛ استثنا باید پررنگ و نیازمند تایید شود. خروجی‌ها محصول/درجه مستقل‌اند و اثر موجودی دارند.

## سبد و ظرف
BasketType دارای کد/نام، رنگ/نوع، وزن خالی، واحد، تاریخ اعتبار، وضعیت و روش کنترل وزن است. وزن tare از داده پایه نسخه‌دار به سند کپی می‌شود؛ سند گذشته با تغییر master data مجدداً محاسبه نمی‌شود. امکان واردکردن وزن واقعی سبد/سری با مجوز، تاریخ اندازه‌گیری، ابزار، نمونه/تعداد اندازه‌گیری و کاربر فراهم شود. سبدهای آبی/سبز/مشکی یا سایر انواع نباید در کد ثابت محدود شوند.

اگر امانت/مالکیت سبد نیاز عملیات است، یک دفتر گردش جدا برای تعداد سبد بر اساس شخص، انبار، رنگ/نوع، تحویل/برگشت/کسری و اختلاف لازم است. وزن میوه و تعداد سبد دو کمیت مستقل‌اند؛ تغییر یکی دیگری را بی‌دلیل عوض نکند. بازگشت سبد به‌تنهایی وزن بار را اصلاح نمی‌کند؛ سند مربوط لازم دارد.

## هزینه‌ها و سود
هزینه حمل، کارگر، شست‌وشو/ضدعفونی، گرمادرمانی، واکس، بسته‌بندی، انرژی/سرمایش و نگهداری باید به صورت هزینه دوره‌ای یا هزینه قابل تخصیص تعریف شوند. اگر هزینه مستقیم به محصول/عملیات تخصیص یافت، معیار (kg، سبد، ساعت، بار یا نرخ ثابت) و نسخه آن ذخیره شود. عدم تخصیص، در گزارش سود به‌عنوان محدودیت نشان داده شود نه اینکه هزینه از خروجی حذف شود.

## گزارش‌ها
موجودی فعلی و گردش با drill-down، مقدار منفی، ورودی-خروجی تجمیعی، ضایعات و علت، بازده سورت، بازده بسته‌بندی، کار در جریان/ارسال امانی، سبد نزد اشخاص و اختلاف امانت، موجودی در راه، شمارش فیزیکی، تعدیلات مجاز، و هزینه محصول. هر عدد باید به حرکت‌های تشکیل‌دهنده قابل بازکردن باشد.

# نظام تجربه کاربری مدرن Mazand FOS — مشخصات قابل پیاده‌سازی

## جهت بصری
رابط ممتاز، معاصر، روشن و صنعتی؛ طراحی اطلاعاتی دقیق، فضای تنفسی کافی، سطوح روشن با کنتراست بالا، خاکستری‌های خنثی و یک رنگ تأکیدی محدود برای اقدام اصلی. رنگ هشدار فقط برای استثنا، نه تزئین. از کارت‌های ریز و پرشمار، گرادیان‌های نمایشی، جدول متراکم بدون سلسله‌مراتب، و فرم قدیمیِ همه‌فیلدها در صفحه بلند پرهیز شود. رنگ به‌تنهایی معنی را منتقل نکند؛ آیکن + برچسب + حالت/متن لازم است.

## چارچوب صفحه
- RTL واقعی در layout، جدول، فرم، منوی راست/چپ، منطق focus و breadcrumb؛ جهت اعداد/شماره‌ها در فیلدهای شناسه/مبلغ با روش bidi کنترل شود.
- header ثابت با نام بخش، مکان‌یابی، وضعیت اتصال (Offline/LAN/Sync pending)، هویت کاربر و دسترسی‌های مرتبط.
- sidebar قابل جمع‌شدن با گروه وظایف: داشبورد، عملیات مرکبات، خرید/فروش، بارفروش/صافی، خزانه/چک، حسابداری، انبار/سورت، اطلاعات پایه، گزارش‌ها، همگام‌سازی، پشتیبان‌گیری و تنظیمات.
- فضای کاری اصلی با ارتفاع viewport؛ هر مرحله فرم در همان ناحیه جایگزین شود، نه انباشته‌کردن بخش‌های بلند عمودی.
- نوار اقدام ثابت پایین در فرم‌های حیاتی: ذخیره پیش‌نویس، اعتبارسنجی، ثبت/قطعی‌سازی، چاپ/پیش‌نمایش و بستن. وضعیت دکمه‌ها و دلیل disable واضح باشد.
- جدول با scroll داخلی، عنوان ستون‌های مهم ثابت، سطر خلاصه ثابت، جست‌وجو/فیلتر/تنظیم ستون و کلیدهای میانبر.
- پنل جانبی برای ایجاد سریع Party/Product/Basket/Account با `return_context`; بعد از ذخیره بازگشت به فرم مادر.

## داشبورد نقش‌محور
داشبورد صرفا مجموعه‌ای از عددهای تزئینی نیست. هر KPI باید عنوان، واحد/بازه زمانی، منبع و timestamp داشته باشد؛ کلیک روی آن با فیلترهای معادل به گزارش مبنا می‌رود. نماها: مدیریت، عملیات و وزن، فروش/بارفروش، مالی/خزانه، کیفیت داده و سلامت sync. نمونه شاخص‌ها: امروز ورودی و خروجی kg، فاکتورهای ناتمام، پرداخت تخصیص‌نیافته، سررسیدهای امروز/عقب‌افتاده، صافی‌های باز، مغایرت وزن، موجودی منفی/تعدیل‌نشده، ردیف بانک بی‌تطبیق، Draftهای GL، اختلاف معین/کل، آخرین Backup و وضعیت آخرین restore test. شاخص فاقد داده، `—` و دلیل نشان می‌دهد؛ صفر جعلی ممنوع.

## فرم فاکتور بدون اسکرول طولانی
بالا: نوع/شماره سند، طرف حساب، تاریخ/انبار/شرط پرداخت، وضعیت و لینک اسناد مرتبط. مرکز: جدول چندردیفی با ستون‌های مرکبات/سبد/باسکول/خالص/افت/قابل‌حساب/نرخ/مبلغ. روی صفحه کوچک، ستون‌های کم‌استفاده به پنل جزئیات row منتقل می‌شوند اما کلیدهای مالی و نتیجه محاسبه پنهان نشوند. پایین ثابت: جمع gross/tare/net/loss/billable، مبلغ قبل/بعد تخفیف، تخصیص/پرداخت/مانده، هشدارهای validation، کنترل موجودی و دکمه‌های اصلی. مرحله‌های تأیید در همان فضای کار تعویض شوند و Draft حفظ شود.

## متن و اصطلاحات
هر کنترل معنادار tooltip کوتاه فارسی دارد: نام، مقصود، واحد/فرمول و اثر بر سند. خطا باید بگوید چه چیزی اشتباه است، چطور اصلاح شود و آیا ثبت متوقف می‌شود. اصطلاح فنی برای مدیر فنی مجاز اما برای اپراتور باید همراه ترجمه کارگاهی باشد؛ مثلاً «وزن قابل‌حساب (کیلو که قیمت بر آن اعمال می‌شود)». کمک زمینه‌ای فارسی بدون اینترنت available است.

## دسترس‌پذیری و اپراتور کم‌سواد
اندازه کلیک مناسب، فونت خوانا، فاصله سطر، رنگ + نماد، صفحه‌کلید کامل، ترتیب tab منطقی، focus visible، tooltip فوری، تأیید برای عمل برگشت‌ناپذیر، نمایش فیلدهای حیاتی قبل از Post، کاهش تایپ تکراری با پیش‌فرض‌های نسخه‌دار، تاریخ شمسی برای نمایش و timestamp استاندارد برای ذخیره. هیچ دکمه حساس فقط آیکن بی‌نام نباشد.

## رفتار تعامل
- Autosave پیش‌نویس باید وضعیت «ذخیره شد/ذخیره در انتظار/خطا» داشته باشد و آخرین ذخیره واقعی را به‌روشنی نمایش دهد.
- عملیات قطعی دکمه در حال کار، disable تا پاسخ و idempotency سمت سرور دارد.
- خطای اتصال نباید مقادیر فرم را پاک کند؛ retry فقط با همان operation id.
- خروج با تغییرات ثبت‌نشده یک dialog با گزینه‌های مشخص ذخیره/بازگشت/خروج داشته باشد.
- ترتیب پیش‌فرض جداول جدیدترین‌به‌قدیمی‌ترین برای timeline، و ترتیب کسب‌وکارمحور برای کدینگ؛ sort هر ستون علامت‌دار و در export حفظ شود.

## نشانگرهای وضعیت
`Draft`، `Pending Approval`، `Posted`، `Reversed`، `Sync Pending`، `Conflict`، `Bank Unmatched`، `Estimate` و `Out of Balance` باید badge + متن داشته باشند و تعریف یکسان در همه ماژول‌ها داشته باشند. badge هرگز تنها راه اطلاع‌رسانی نباشد.

# INFO و Excel: الگوهای داده پایه، import/export و سازگاری Office 2013

## نقش INFO و دفترهای قدیمی
دفتر INFO و شیت‌های عملیاتی/مالی legacy باید قبل از mapping واقعی فهرست و نمونه‌برداری شوند. نام‌هایی که در گفت‌وگوها به‌عنوان ساختار محتمل آمده‌اند: `Dashboard`، `Harvest/برداشت` (انبار قاسم)، `Transfer/انتقال` (انبار مرتضی)، `Morteza Sales`، `Qasem Sales`، `INFO` و `Settlements/تسویه`. این نام‌ها باید به‌عنوان نام‌های کشف‌شونده فرض شوند، نه تضمین وجود دقیق در فایل فعلی. هیچ سطر یا فرمولی بدون بازکردن نمونه واقعی، معنای قطعی فرض نشود.

## مدل مرجع و Template Registry
هر الگوی Excel دارای template ID و version، نام فارسی، نوع سند/داده، schema مقصد، ستون‌های مورد انتظار، نوع هر ستون، فرمول‌ها، ورودی اجباری/اختیاری، قواعد نرمال‌سازی، کلید duplicate، نگاشت روابط و سیاست خطاست. نسخه تغییرکرده نباید فایل‌های قدیمی را بی‌هشدار بر اساس ستون هم‌نام غلط وارد کند.

الگوهای حداقل: Parties، Accounts/COA، Products، BasketTypes، Banks/BankAccounts، Warehouses، Opening Balances، Harvest/Inbound، Transfer، Purchase invoices، Sales invoices، Barforoosh loads، Sales reports، Safi settlements، Treasury transactions، Cheque register، Expenses, inventory counts/adjustments، bank statements. در صورت واردات/خروجی، نوع سند و واحد، ارز و تاریخ حتما مشخص است.

## Wizard ورود
1. انتخاب فایل/شیت/ناحیه و encoding/فرمت.
2. تشخیص header و preview، بدون هیچ commit.
3. کاربر نوع الگو را انتخاب می‌کند یا mapping ذخیره‌شده را بارگذاری می‌کند.
4. mapping ستون خام → فیلد مرجع به‌همراه تبدیل/فرمت و sample value نمایان است.
5. normalize: ارقام فارسی/لاتین، فاصله/نیم‌فاصله، تاریخ شمسی/میلادی، اعشار/جداکننده هزارگان، وزن/پول و کدهای با صفر ابتدایی با احتیاط.
6. validation: الزامی، type, referential integrity، تاریخ، مبلغ/وزن، رابطه Party، موجودیت ناشناخته، حساب غیرفعال، کد تکراری و محاسبه مورد انتظار.
7. duplicate candidateها بر اساس شناسه/کد و ترکیب معنا، نه فقط نام. گزینه‌ها: Skip, Match existing, Merge with explicit mapping, Create new, Reject row. سیستم نباید overwrite پیش‌فرض داشته باشد.
8. summary کل batch: تعداد معتبر، هشدار، رد، duplicate، روابط حل‌نشده، اثر پیشنهادی و مثال‌های نماینده.
9. Commit اتمیک پیش‌فرض: خطای بحرانی مانع commit کل batch است. ورود جزئی فقط انتخاب روشن با گزارش ردیف‌های reject شده.
10. receipt/import log دارای شناسه، hash فایل، template/version، کاربر، زمان، تعداد، errors/warnings و امکان بازکردن هر ردیف اصلی.

## قواعد داده و Excel
- کد حساب، کد کالا، شماره چک و شناسه‌های دارای صفر ابتدایی باید در فرمت Text نگهداری شوند؛ Excel نباید آن‌ها را به number/scientific notation تبدیل کند.
- مقادیر پول و وزن cell عددی با number format مناسب باشند، نه رشته متنی با جداکننده‌ها.
- تاریخ باید فرمت واقعی تاریخ داشته باشد و شکل نمایش با تنظیم منطقه/شمسی سازگار باشد؛ مقدار خام و نوع تبدیل در import log حفظ شود.
- ستون‌های محاسباتی درصد/کیلو یا مقدار/درصد، فرمول و مقدار مرجع را توضیح دهند. خروجی باید قابل‌ردیابی باشد، نه پر از فرمول‌های شکسته یا hidden logic.
- workbook ساختار منطقی، فیلتر، Freeze Panes، Print Titles، عرض ستون، عنوان و footer/شماره صفحه، فرمت خطا/جمع و راهنمای sheet داشته باشد. ورودی‌های متعدد data validation داشته باشند در صورت پشتیبانی نسخه هدف.
- Office 2013 نباید به XLOOKUP، LET، FILTER/UNIQUE پویا، spill arrays یا هر تابع جدید به‌عنوان پیش‌نیاز وابسته شود. از فرمول‌های قدیمی سازگار یا محاسبه سمت برنامه استفاده شود؛ نتیجه نهایی با ارزش محاسبه‌شده ذخیره شود اگر نیاز است خروجی در Excel قدیمی بدون recalculation درست دیده شود.
- CSV برای جابه‌جایی ساده مفید است اما قالب گزارش حرفه‌ای با چند sheet، فرمول و چاپ را جایگزین نمی‌کند.

## خروجی‌گیری
هر گزارش/داده خروجی باید زمان تولید، فیلترهای فعال، وضعیت رکوردها، واحدها، ارز/ریال/تومان نمایشی، سیاست round، ستون‌های انتخاب‌شده و شماره نسخه قالب را ثبت کند. صادرکردن بانک/شخص/داده حساس مجوز عملیاتی می‌خواهد و audit رخداد export ثبت شود. هنگام نمایش تومان، فایل باید نشان بدهد مبنای ذخیره ریال است و ضریب نمایش 10 بوده است؛ تبدیل نباید به ارزش مرجع برگردانده شود.

## همگام‌سازی چند Excel یا چند دستگاه
فایل Excel مرجع truth مستقل برای ویرایش هم‌زمان چند کاربر نیست. Import باید snapshot، شناسه رکورد و hash/version قبلی را بشناسد. اگر ورودی بر اساس snapshot قدیمی تغییر کرده، stale-update conflict ایجاد شود؛ به‌صورت last-write-wins overwrite نشود. ادغام با mapping شناسه پایدار و گزارش تغییرات انجام شود. چند دفه import همان فایل/ردیف باید duplicate detection و idempotency داشته باشد.

## آزمون Office 2013
صرف ساخت فایل توسط کتابخانه کدنویسی کافی نیست. روی محیط واقعی Office 2013 یا VM معتبر: بازکردن بدون repair warning؛ محاسبه فرمول؛ sort/filter؛ حفظ صفر ابتدایی؛ تاریخ/عدد فارسی؛ چاپ/Print Preview؛ صفحه‌بندی؛ Freeze Panes؛ chartها؛ اعتبارسنجی ورودی و فشرده‌سازی/ارسال فایل آزمایش شود. اگر محیط آزمون موجود نیست، وضعیت «سازگاری اثبات‌نشده» ثبت شود و ادعای pass نکنید.

# معماری آفلاین، شبکه محلی، چنددستگاهی و حل تعارض

## دو پروفایل اجرا، نه یک فرض مبهم
**Standalone Offline:** یک دستگاه با دیتابیس محلی؛ عملیات مجاز به‌صورت محلی ذخیره می‌شوند. ارقام در همان دستگاه معتبرند؛ گزارش مجموعه‌ای تا زمان انتقال/همگام‌سازی معتبر نمایش داده نمی‌شود.

**LAN Shared:** سرویس برنامه و پایگاه داده مرجع در رایانه/سرویس مرکزی داخل شبکه محلی. ایستگاه‌ها از API به آن متصل می‌شوند؛ قطع اینترنت نباید عملیات LAN را متوقف کند. این معماری با قرار دادن فایل دیتابیس SQLite روی پوشه share تفاوت دارد؛ فایل writable مشترک روی network filesystem ممنوع است.

**Sync/Transfer:** انتقال کنترل‌شده بین یک دستگاه مستقل و مرجع، شامل preview، UUIDهای رویداد، idempotency، mapping ارجاعات، duplicate detection، conflict queue و گزارش نتیجه. Sync موفق باید بر اساس receipt قابل اثبات باشد، نه فقط «upload started».

## مدل رویداد همگام‌شونده
هر رویداد قابل انتقال شامل entity UUID، event UUID، device ID، local sequence، entity version/revision، زمان دستگاه و زمان دریافت مرکزی (اگر موجود)، actor، نوع عملیات، payload version، references، idempotency key، origin/source، checksum و وضعیت sync است. timestamp واقعی فقط وقتی منبع معتبر دارد؛ clock drift شناسایی و برچسب‌گذاری شود.

## Outbox و inbox
تغییر محلی و outbox event در یک تراکنش ذخیره می‌شوند. ارسال می‌تواند دوباره retry شود؛ سرور inbox/processed-event به کمک event UUID و idempotency از اجرای تکراری جلوگیری می‌کند. پاسخ سرور شامل شناسه رسید، وضعیت پذیرفته/تکراری/رد/تعارض و خطای اعتبارسنجی است. رویداد ردشده از صف خاموش پاک نمی‌شود.

## Conflict policy
last-write-wins برای اسناد مالی/حسابداری ممنوع است. تعارض‌ها دسته‌بندی شوند: تغییر دوطرفه یک فیلد؛ ویرایش بعد از Post؛ شماره/کد یکتای تکراری؛ تخصیص هم‌زمان یک پرداخت؛ دو دستگاه با موجودی/مانده ناسازگار؛ مرجع حذف/غیرفعال‌شده؛ نرخ/الگوی متفاوت؛ ترتیب رخداد نامعلوم. هر مورد راه‌حل اختصاصی دارد: انتخاب مالک تغییر، merge فیلدی برای فیلدهای بی‌اثر، رد با علت، ایجاد اصلاحیه، یا بررسی دستی. اطلاعات مرجع/تعارض و مقدار قبل/بعد حفظ شود.

## شماره‌گذاری و شناسه
شناسه داخلی UUID پایدار است؛ شماره خوانای فاکتور می‌تواند در profile محلی prefix/sequence داشته باشد تا collision رخ ندهد یا هنگام sync شماره مرکزی تخصیص و شماره محلی به‌عنوان alias حفظ شود. پرامپت عامل باید این مسئله را قبل از پیاده‌سازی تصمیم‌گیری و مستند کند؛ تولید دو شماره ظاهراً یکسان ممنوع است. شماره سند قطعی نباید صرف retry عوض شود.

## انتقال Excel یا انتقال backup
انتقال batch با manifest شامل نسخه schema، منبع، تعداد رویدادها، checksum، وابستگی‌ها و زمان export. دریافت ابتدا validate-only و preview انجام می‌دهد؛ سپس transactionها commit می‌شوند. داده‌ای که به مرجع ناشناخته ارجاع دارد در quarantine می‌ماند. نتیجه باید تعداد accepted, duplicate, conflict, rejected, deferred و شناسه گزارش را ارائه کند. Backup image برای disaster recovery است، نه راهکار merge دو دیتابیس.

## سازگاری و محدودیت‌های امنیتی
- پایگاه مرجع و نسخه‌های local باید migration نسخه‌دار داشته باشند؛ client جدید با server قدیمی ناسازگار در سطح قابل تشخیص پیغام بدهد.
- Windows 7 در صورت باقی‌ماندن به‌عنوان نیاز legacy فقط با تست واقعی local/LAN؛ remote exposure از آن فرض نمی‌شود. دسترسی بیرونی از VPN/gateway امن و محیط پشتیبانی‌شده.
- هیچ‌وقت credential یا database file از طریق sync log/Excel ساده صادر نشود.
- sync باید در صفحه سلامت با شمار آخرین ارسال موفق، صف مانده، conflict، خطای آخر، نسخه schema و شناسه دستگاه نمایش داده شود.

## معیار پذیرش
قطع اینترنت در حالت LAN؛ قطع LAN در وسط ثبت محلی؛ restart قبل از ارسال outbox؛ retry بعد از پاسخ گم‌شده؛ duplicate event؛ دو دستگاه با یک پرداخت؛ تغییر حساب/Party آفلاین و غیرفعال شدن مرکزی؛ migration کلاینت؛ ساعت دستگاه اشتباه؛ export/import batch ناقص؛ بررسی مانده مرکزی تا قبل/بعد sync. در هر مورد، عدم فقدان/تکرار و گزارش صحیح نتیجه اثبات شود.

# امنیت، مجوز، پشتیبان، نصب، ارتقا و انتشار

## هویت و دسترسی
کاربر مستقل یا الگوی مجوز تأییدشده برای هر نقش؛ حساب اشتراکی کمینه شود تا audit فردی از بین نرود. نقش‌ها می‌تواند مدیر، حسابدار، فروش، خرید، انبار، باسکول، سرپرست، خزانه‌دار، مشاهده‌گر و نقش سفارشی باشد. مجوز صرفا page-level نیست؛ عمل حساس مانند مشاهده قیمت خرید، تخفیف، وزن، مانده، Post، reversal، تغییر کدینگ، import/export، backup/restore، تغییر نقش و reopen دوره کنترل می‌شود. least privilege؛ پیش‌فرض deny؛ ثبت تلاش دسترسی ناموفق؛ rate limiting و password hashing امن؛ مدیریت session و logout؛ secrets خارج از repo و log. برای remote/admin، MFA یا محافظت تکمیلی در صورت پشتیبانی.

## اطلاعات حساس و audit
شماره حساب/شبا، اطلاعات تماس، فایل قرارداد و backup با کمترین دسترسی و در صورت نیاز رمزگذاری شوند. log عملیاتی نباید رمز، token یا اطلاعات بانکی کامل را بازتاب دهد. Audit append-only از ایجاد/تغییر/تایید/ابطال/Export/Import/Login/Permission/Backup/Restore نگهداری کند؛ شامل actor، زمان منبع، device، نوع رویداد، شناسه هدف، مقدار قبل/بعد با masking حساس و دلیل. دستکاری audit باید شناسایی‌پذیر باشد.

## Backup
حداقل: هنگام خروج تمیز، زمان‌بندی قابل تنظیم، قبل از migration/upgrade/restore یا عملیات پرخطر. سیاست retention قابل تنظیم، چند نسل نسخه، مسیر ذخیره مجزا از دیتابیس اصلی و کپی آفلاین/رسانه جدا؛ backup بیرونی رمزگذاری شود. هر snapshot manifest، timestamp، نسخه برنامه/DB، checksum، اندازه، وضعیت و نتیجه دارد. خطای backup باید در داشبورد و log با هشدار قابل مشاهده باشد؛ وجود فایل تنها مساوی سالم بودن نیست.

## Restore drill
در محیط جداگانه restore شود؛ checksum، بازشدن DB، تعداد جدول/رکورد، foreign key/integrity check، حساب توازن، تعداد اسناد مالی، چند query کلیدی، شمار اسناد منبع/GL و کارایی حداقلی بررسی شود. گزارش شامل زمان شروع/پایان، نسخه backup، نتیجه و اختلاف‌ها باشد. Restore روی داده زنده بدون تأیید و snapshot قبلی ممنوع.

## نصب و ارتقا
بسته قابل انتشار باید شامل installer/portable package متناسب با تصمیم معماری، وابستگی‌ها، migrationها، فایل نمونه config بی‌راز، راهنمای نصب، راهنمای admin، نسخه/commit، hash/checksum، release notes، محدودیت‌ها، دستور backup/restore و دستور rollback باشد. نصب اولیه، ارتقای نسخه موجود، downgrade ممنوع یا مدیریت‌شده، قطعی برق وسط migration و شکست migration آزمایش شود. Migration قبل از تغییر schema backup معتبر می‌گیرد، تراکنش یا روند قابل ادامه دارد و نسخه schema را ثبت می‌کند.

## GitHub و مدیریت سورس
مخزن Private `mazand-fos`؛ شاخه محافظت‌شده main؛ pull request با review/checks؛ ممنوعیت force push و secret؛ branch کوتاه‌عمر؛ tag نسخه؛ GitHub Actions فقط با permission کمینه. `.gitignore` باید DB، فایل‌های مشتری، exportها، backup، secrets، env، نصب‌کننده/artefactهای حجیم و داده واقعی را پوشش دهد. داده مصنوعی فقط برای نمونه. قبل از upload، git status/diff و scan راز و داده حساس بررسی شود. license متن‌باز بدون تایید مالک اضافه نشود.

## لحظه انتشار
1. freeze scope و ثبت Release Candidate commit.
2. اجرای full test suite و regression روی سیستم پاک و نسخه ارتقایی.
3. تست migration واقعی روی کپی ناشناس/آزمایشی، تطبیق count/weight/money totals.
4. restore rehearsal از backup تازه.
5. اثبات Office 2013 / Windows 7 فقط اگر محیط‌های مربوط واقعاً تست شده باشند.
6. چک مجوزها، security scan، رازها و فایل‌های ناخواسته.
7. تولید installer، ثبت checksum امضا/هش، release notes، known limits و گزارش آزمون.
8. تایید مالک برای انتشار و سپس publish/tag/upload. عامل نباید بدون اجازه صریح push یا release بسازد.
9. بعد انتشار: smoke test، log، health/sync/backup check و مسیر rollback.

## محدودیت ایمنی
بسته مستندات نمی‌تواند امنیت واقعی یا نصب موفق را ثابت کند. این ادعاها فقط بعد از آزمون محیط هدف و شواهد قابل بازتولید مجازند.

# کاتالوگ پذیرش و سناریوهای رگرسیون

هر آزمون باید ID، پیش‌شرط، داده تست مصنوعی، گام‌ها، نتیجه مورد انتظار، نتیجه واقعی، artifact/log، محیط، version/commit، وضعیت و مسئول داشته باشد. «کلیک کردم کار کرد» یا آزمون صرفا تصویری برای موتور مالی کافی نیست.

## مالی/کدینگ

# طرح بررسی Excelهای قدیمی و نگاشت داده‌های مازندشت

## قبل از Import
هیچ workbook واقعی را مستقیماً به محیط production وارد نکنید. یک کپی محدود/ناشناس‌شده در محیط staging تهیه شود. فایل‌های اصلی read-only حفظ شوند و hash، زمان دریافت، نام شیت، تعداد سطر/ستون، فرمول‌ها، named ranges، hidden rows/columns، merged cells و نوع داده ستون‌ها ثبت شود.

## نگاشت پیشنهادی نام‌های شناخته‌شده
`Harvest/برداشت` را ابتدا به ورود از باغ و/یا قبض باسکول نگاشت کنید، نه به Purchase payable به‌طور خودکار. `Transfer/انتقال` ممکن است انتقال انبار/محموله باشد؛ مشخص شود آیا جفت ارسال/دریافت دارد. `Morteza Sales` و `Qasem Sales` نام sheet فروش هستند ولی نقش seller/warehouse/owner باید از داده و گردش واقعی تایید شود. `Settlements/تسویه` ممکن است صافی بارفروش باشد یا پرداخت/settlement؛ نوع هر ردیف از ستون/سند منبع تعیین شود. `Dashboard` عموما خروجی aggregation است و به‌عنوان سند اصلی import نشود. `INFO` احتمالاً داده پایه است؛ duplicate/key relationships بررسی شود. اینها فرضیه نگاشت‌اند نه حقیقت تاییدشده.

## تطبیق و گزارش مهاجرت
پیش/پس از واردسازی: تعداد طرف‌حساب یکتا؛ کالاها/انبارها/سبدها؛ تعداد و مجموع وزن قبض‌ها/فاکتورها؛ فروش/خرید به تفکیک بازه؛ مبالغ دریافت/پرداخت؛ مانده باز هر شخص؛ ردیف‌های صافی و هزینه‌ها؛ موجودی تجمعی/کسری؛ bank statement rows؛ چک‌های باز؛ بدهکار/بستانکار؛ حساب‌های واسط. اختلاف صفر فرض نشود؛ اختلاف‌ها بر اساس علت (duplicate، missing link، unit conversion، rounding، legacy formula) دسته‌بندی شوند. مهاجرت واقعی فقط پس از dry-run و sign-off انجام شود.

## قانون شناسه
شناسه legacy در فیلد `legacy_source_id` و نگاشت به UUID مرجع حفظ شود. اگر کلید مطمئن نیست، با composite identity و review استفاده شود. شماره ردیف Excel شناسه یکتای تجاری نیست مگر رابطه و پایداری آن اثبات شده باشد. هیچ رکورد مالی صرفا از روی شباهت نام خودکار merge نشود.

# فرهنگ داده مرجع و قواعد موجودیت‌ها

این فرهنگ، قرارداد سطح مفهومی است. نام جدول و نوع فیلد نهایی با معماری repo تعیین می‌شود، اما معنای داده، کلیدها و invariants باید حفظ شوند.

## قواعد مشترک تمام رکوردها
- شناسه داخلی پایدار UUID؛ کد/شماره خوانا مستقل از UUID؛ tenant/company scope اگر چند شرکت/دفتر پشتیبانی شد.
- `created_at`/`updated_at` با UTC/offset معتبر در storage؛ نمایش محلی/شمسی لایه UI. زمان واقعی منبع با `source_timestamp` از زمان دریافت/ثبت سیستم جداست؛ ساعت ساختگی ممنوع.
- `created_by`, `updated_by`, `device_id`, `revision/version`, `status`, `source_type`, `source_id`, `idempotency_key` در جایی که semantics دارد.
- فیلدهای مالی/وزنی به نوع decimal دقیق با scale روشن؛ float برای مانده و وزن مالی استفاده نشود. واحد به همراه مقدار/نسخه snapshot ذخیره شود.
- `null` یعنی نامشخص/ثبت‌نشده؛ `0` به معنی صفر واقعی است. نمایش، import و report این دو را یکی نکنند.
- موجودیت referenced حذف فیزیکی نمی‌شود؛ archive/deactivate/status انتقالی؛ change history برای داده حساس/مرجع.

## Print/statement builder minimum
User can choose show/hide allowed columns, row groupings, table width, paper size/orientation, header/footer, signature titles, date/number formats, totals, page break behavior and print labels. Each template is versioned and permission controlled. Invoice/account book use can display a per-row or per-document number according to template needs. Export and print must preserve source document numbers and units; a screenshot-like PDF without selectable totals doesn't replace structured report data.

## Accessibility and low-literacy requirements
- visible label, tooltip and optional inline example for weight/account/payment fields.
- warnings with action and severity; separate non-blocking warning from blocking validation.
- tab order follows workflow; Enter applies contextual cell behavior but never accidentally posts a financial document without explicit intent.
- all important action buttons labeled; destructive/reversal action asks for reason and confirmation.
- empty state teaches next action; error states retain draft; unsupported feature clearly marked.

# نحوه رساندن این بسته به عامل کدنویسی بدون شکستن ممیزی اولیه

## اگر کد پروژه در GitHub است و این بسته هنوز در repository نیست
1. این ZIP را در گفت‌وگوی عامل/Work به‌عنوان context یا فایل پیوست بده؛ مسیرهای داخل بسته باید قابل خواندن باشند.
2. ابتدا فقط Prompt 00 و Prompt 01 را اجرا کن. در Prompt 01 تاکید شده که مخزن هدف فقط‌خواندنی بماند؛ فایل‌های مرجع از داخل خود مخزن خوانده شوند اگر موجودند، و فایل‌های این بسته فقط منبع نیازهای هدف باشند.
3. اگر promptهای اولیه مورد درخواست در مخزن هدف وجود ندارند، گزارش missing تهیه شود. پیش از تایید ممیزی، این بسته را خودکار در مخزن کپی نکن.
4. پس از مرور و تایید خروجی audit و traceability، تصمیم بگیر اسناد canonical کدام مسیر در repository داشته باشند. سپس فایل‌های `PROJECT_SPEC.md`, `docs/01..21`, `prompts/`, `assets/`, templates و release checklist را در branch کاری جدا وارد کن؛ source-baseline را می‌توان در `docs/archive/requirements-baseline/` یا artifact داخلی نگه داشت، ولی هیچ سند خام حذف نشود.
