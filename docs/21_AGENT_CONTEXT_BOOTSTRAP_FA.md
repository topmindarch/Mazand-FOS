# نحوه رساندن این بسته به عامل کدنویسی بدون شکستن ممیزی اولیه

## اگر کد پروژه در GitHub است و این بسته هنوز در repository نیست
1. این ZIP را در گفت‌وگوی عامل/Work به‌عنوان context یا فایل پیوست بده؛ مسیرهای داخل بسته باید قابل خواندن باشند.
2. ابتدا فقط Prompt 00 و Prompt 01 را اجرا کن. در Prompt 01 تاکید شده که مخزن هدف فقط‌خواندنی بماند؛ فایل‌های مرجع از داخل خود مخزن خوانده شوند اگر موجودند، و فایل‌های این بسته فقط منبع نیازهای هدف باشند.
3. اگر promptهای اولیه مورد درخواست در مخزن هدف وجود ندارند، گزارش missing تهیه شود. پیش از تایید ممیزی، این بسته را خودکار در مخزن کپی نکن.
4. پس از مرور و تایید خروجی audit و traceability، تصمیم بگیر اسناد canonical کدام مسیر در repository داشته باشند. سپس فایل‌های `PROJECT_SPEC.md`, `docs/01..21`, `prompts/`, `assets/`, templates و release checklist را در branch کاری جدا وارد کن؛ source-baseline را می‌توان در `docs/archive/requirements-baseline/` یا artifact داخلی نگه داشت، ولی هیچ سند خام حذف نشود.
5. پیش از merge، تفاوت نیازمندی‌های repo موجود با بسته v4 در decision log ثبت شود؛ فایل هم‌نام را با overwrite کورکورانه جایگزین نکن.

## اگر عامل به محتوای ZIP/فایل‌ها دسترسی مستقیم ندارد
Promptها را یکی‌یکی paste کن و همراه آن، سند canonical مربوط به همان مرحله را ضمیمه/باز کن. اگر prompt به سندی اشاره می‌کند که به عامل ارائه نشده، اجرای تغییرات متوقف شود و همان سند درخواست/ارائه شود؛ خلاصه‌سازی ذهنی سند جایگزین خواندن آن نیست.

## مرز اختیارات
تحلیل و ساخت branch/artifact می‌تواند طبق مجوز مشخص انجام شود؛ تغییر repository واقعی، migration داده واقعی، استفاده از اطلاعات مشتری و push/release نیاز به کنترل و مجوز جدا دارد. داشتن این بسته به‌تنهایی به معنای اجازه انتشار نیست.
